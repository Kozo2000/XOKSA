# xoksa Security Design

[日本語ドキュメントはこちら。](#ja)

xoksa is designed with a focus on data safety, calculation consistency, and system availability to ensure reliability as an investment analysis tool.

This document details xoksa's implementation policy based on the CIA (Confidentiality, Integrity, Availability) security properties. In particular, "accuracy," which is the foundation of an analysis tool, is redefined as the top priority and implemented as follows.

---

## 0. Shift-Left Security — Design Goal

**This project aims to treat security as a starting point of design decisions, not a constraint bolted on after the fact.**

This project aims for a Shift-Left Security posture. Contributors — human and AI — strive to follow these principles:

> **The goal is that security is not only designed but checked against the exact binary shipped** — we aim to inspect every release and bind the result to that binary's hash. The web server's serve-mode design controls are in §4; the point-in-time vulnerability assessment (findings, verified-safe classes, and a penetration-testing playbook), together with its binding to the shipped binary's hash, is recorded in [**security-assessment.md**](./security-assessment.md).

- **Security first**: Before writing any code that touches API keys, credentials, external input, or sensitive data, consult this document and aim to keep the design consistent with it. Implementation follows design; design does not follow implementation.
- **Security not as an afterthought**: The aim is to avoid retrofitting security onto a working implementation; a "works but insecure" state is not treated as an acceptable stopping point.
- **Identify assets before writing code**: Before writing any code that handles data, enumerate every information asset the code will create, store, transmit, or process. Apply the identification criteria in Section 0.1 to each asset. A security measure cannot be applied to an asset that has not been identified.
- **Violations are taken seriously**: A security violation found by audit is, as far as practical, treated as a blocking defect rather than deferred — "it works" is not by itself a reason to postpone a fix.

These principles apply equally to new features, refactors, and incremental changes. When in doubt, stop and verify against this document before proceeding.

**Language synchronization rule:** The English and Japanese sections are both normative. Security requirements are interpreted as the union of both language sections. If one language contains a requirement, exception, or restriction that is missing from the other, that requirement still applies and the missing side must be updated. Such a mismatch is a documentation defect, not a change in security policy.

## 0.1 Protected Asset Identification

Assets in this project are grouped into two natural categories:

- **Private data**: Data relating to the user's credentials, environment, or network configuration. Examples: API keys, passwords, authentication tokens, Ollama server IP address.
- **Public data**: Data obtained from or derived from publicly accessible sources. Examples: stock prices, calculated technical indicators, fundamental data, news articles.

For each category, security requirements are derived by evaluating impact across all three CIA dimensions:

- **Confidentiality**: does exposure cause harm?
- **Integrity**: does modification or contamination cause harm?
- **Availability**: does loss of access cause harm?

The protection class assigned to each asset reflects this three-dimensional evaluation. Implementation techniques are detailed in Section 1 (Integrity), Section 2 (Confidentiality), and Section 3 (Availability).

The tables below record the asset groupings and their protection requirements.

### Class A — Credentials (full protection required)

| Asset | Description |
| :--- | :--- |
| `OPENAI_API_KEY` | OpenAI API key |
| `GEMINI_API_KEY` | Google Gemini API key |
| `CLAUDE_API_KEY` | Anthropic Claude API key |
| `BRAVE_API_KEY` | Brave Search API key |
| `JQUANTS_API_KEY` | J-Quants API key (v2 — the only J-Quants credential) |
| `NOTIFY_<n>_SECRET` | Chat-notification webhook token/path or bot token (grants posting to the user's channel) |
| `SERVE_AUTH_TOKEN` | Auto-generated bearer token that gates a non-loopback `serve` (remote/distributed access); the only Class A key shown to the operator on demand |

**Protection requirements:**
- Stored in OS Keychain via `--init` / `--update-key`; `xoksa.env` entries take priority when present (exception: `SERVE_AUTH_TOKEN` is **auto-generated by the engine and stored there itself**, not user-registered — see §4)
- Each managed key occupies its own OS Keychain entry (`Entry("xoksa", "<KEY_NAME>")`)
- Retrieved on-demand only — immediately before the API request that requires the key, nowhere else
- Passed through the entire call chain as `Zeroizing<T>`; never unwrapped to a plain `String`. Exception: the file parser (`xoksa.env` loader) uses standard `String` for line buffering and value extraction; these intermediates have minimal lifetime and are destroyed on function return. All values passed beyond the loader boundary are `Zeroizing<T>`.
- Never stored in `env_map` or `Config`
- Never written to logs, debug output, or LLM prompts
- Shown only as present/absent in `--doctor` / `--check-keys`; actual values never displayed. **Exception — `SERVE_AUTH_TOKEN`:** because it is auto-generated (the operator never chose it) and a remote client must be given it, it is shown to the operator on demand (`xoksa serve --show-token`, and once at first generation); safe because the operator is inside the OS trust boundary. Retrieval for existence diagnosis is an explicitly permitted exception to the on-demand rule; the retrieved value is `Zeroizing<T>` and immediately discarded. Unnecessary key reads outside of API call paths should be avoided.

**HTTP header transmission boundary exception:**
- `JQUANTS_API_KEY` (`x-api-key` header): at the HTTP request boundary the key is passed as `&str` (`&**api_key`) into `.header("x-api-key", …)`. `reqwest` copies it into an internal `HeaderValue` that does not implement `Zeroize`; this is an accepted exception at the final transmission step. The `Zeroizing<String>` original is retrieved on demand and dropped when the request completes.
- The same boundary applies to every other Class A key sent as an HTTP header: the OpenAI / Gemini / Claude keys on both the analysis calls and the `/llm net` model-list query, and the `NOTIFY_<n>_SECRET` bearer token on a LINE push. Each is passed as a borrowed `&str` — the OpenAI key and the LINE token through `reqwest`'s `bearer_auth`, which assembles the `Bearer …` value inside `reqwest` — and `reqwest` performs the single, accepted copy into its non-`Zeroize` `HeaderValue`. No owned `String` holding a key is created in xoksa's own code, and nothing here builds that header value itself. *(Corrected 2026-10-01: this said the OpenAI `Bearer …` value was built in a `Zeroizing` buffer. It is not, and never was; letting `reqwest` assemble it is the stronger of the two, because it removes the buffer rather than clearing it afterwards.)*

> **Note:** Authenticated proxy URLs (`user:password@...`) are not supported at the application level. Proxy authentication must be configured at the OS level.

### Class B — User-identifying configuration (basic consideration)

| Asset | Description |
| :--- | :--- |
| `SEC_USER_AGENT` | App name + email required by SEC EDGAR (public identifier, not a secret) |
| Proxy host / port | Operational routing info (no credentials) |
| Ollama host / port | Connection info for local Ollama server |
| User input context | Chat messages, `-x` arguments, and `~/.xoksa_history` |
| Debate buffer | Bounded context window: LLM response excerpts and the user turns that prompted them (`entry.user`) |

**Protection requirements:**
- Stored in `xoksa.env` only; no OS Keychain required
- Not written to logs unnecessarily
- Values masked in display output where shown alongside credentials
- Ollama connection info may be displayed in `--doctor`, `/llm`, and `--debug-ollama`; this display is permitted
- **The UI language is a setting, not a per-surface preference.** `LANG` in `xoksa.env` is its single source: the CLI, the dashboard (stamped into the page the engine serves), the connection screen, and the settings app all read that one value, and the dashboard's selector writes it back rather than keeping a copy. The OS locale is only the first-run fallback, before a config exists. Writing is **loopback-only** — a LAN client is served the configured language but must not rewrite settings on the operator's machine — and a `--private` session refuses the write instead of reporting one
- Chat history (`~/.xoksa_history`) is stored under OS file permissions (0600); `Zeroizing` is not required. A `--private` session neither reads nor writes it — the file records the user's own typed lines, which is exactly the trace a no-trace session rules out (arrow-key recall stays in memory)
- User input and debate buffer contents are transmitted to the selected LLM provider when cloud mode is active; this transmission is by design and user-acknowledged
- `Zeroizing` is **not** required — these are not credentials

### Class C — Calculated and public data

All other data handled by xoksa falls into this class. Whether to apply additional security measures is assessed per asset using the CIA evaluation defined in Section 0.1:

- Technical indicators and scores (RSI, MACD, EMA, Fibonacci, etc.) — derived from public market data
- News article titles and URLs — publicly accessible information
- Standard analysis LLM prompts and responses — constructed from Class C data only (no user input)
- Configuration values (STANCE, thresholds, indicator weights, analysis mode, etc.)
- Ticker symbols and company names
- Log files (technical analysis results)

> **Note:** Chat-mode LLM prompts are assembled from both Class C data and Class B content (user turns, Debate Buffer). Those prompts inherit Class B handling for the Class B portions — they are transmitted to the selected LLM provider by design and user-acknowledged, and must not be written to logs.

Applying `Zeroizing`, secure storage, or on-demand access patterns to Class C assets is generally unnecessary. Whether to apply them should be judged by weighing the security benefit against the impact on usability and maintainability. Blanket application to non-sensitive data obscures which assets are truly sensitive and makes the codebase harder to reason about.

## 0.2 Threat Model

xoksa runs as a **local, single-user tool**. The design defends the boundaries below; the controls are detailed in §§1–4, and the point-in-time review is in [security-assessment.md](./security-assessment.md). To report a vulnerability, see [SECURITY.md](../../SECURITY.md).

**Trust boundaries:** browser ↔ local server; local server ↔ external providers (Yahoo / Stooq / Brave / LLM / chat-notification targets); process ↔ OS keyring. **Desktop app (Tauri):** WebView ↔ desktop Rust via Tauri IPC (in-process), and the desktop and the settings app (`xoksa-setup`) ↔ engine via child processes (the desktop runs `xoksa serve`; the settings app runs the config subcommands); see §6.

**In scope — attackers the design defends against:**
- **A malicious web page open in the same browser** — the primary threat for the loopback default: drive-by requests / CSRF against `localhost`, and attempts to reach another session's data. Countered by per-client session isolation, `SameSite=Strict` cookies, server-side origin checks, and the `Json<T>` content-type gate (§4).
- **Malicious upstream data** — news titles/URLs and market feeds are untrusted input rendered in the browser. Countered by output-encoding + a strict CSP, URL scheme-checking, and treating news as non-SOT "candidate" material (§§1, 4). Where the host is not fixed in code — the Ollama path, plaintext HTTP to a host the user configures — the response body is also size-capped **as it arrives decoded**: `reqwest` requests and inflates compressed bodies by default, and a declared `Content-Length` counts only the compressed bytes, so a small body can otherwise expand without bound (measured: 406 KB → 202 MB → 784 MB RSS).
- **A compromised or vulnerable dependency** — countered by SCA (`cargo audit` + `cargo deny` for advisories **and** license/source compliance, plus `cargo machete` to prune unused deps, on every push) and memory-safe Rust with **`#![forbid(unsafe_code)]`** (compiler-enforced — xoksa's own code contains no `unsafe`); release builds are `--locked`, and a CycloneDX SBOM (`sbom/`) — generated from a throwaway `cargo auditable` build that is not shipped — inventories every component for downstream analysis.
- **Local disk / log inspection** — countered by keeping API keys in the OS keyring (never on disk in plaintext, zeroized in memory), never logging secret values, and `--private` no-trace sessions (§2).
- **A malicious or weak LLM response** — the model can only *explain* program-computed values; an integrity guard drops any figure it invents, and forecasts are labeled non-SOT (§1).
- **A tampered download** — countered by a published SHA-256 per artifact and by binding the shipping inspection to that hash (§4, [security-assessment.md](./security-assessment.md)).

**Explicitly out of scope (by design):**
- **A local attacker already running as the user's OS account** — code running with the user's own privileges is inside the OS trust boundary; xoksa cannot defend against it, and shared-PC isolation is the OS's job (separate accounts).
- **Non-loopback exposure (`--host 0.0.0.0`)** — fail-closed: the server refuses to start without an auth token, accepts only private/loopback source addresses, and safe remote use is kept **inside a trusted private network** (a LAN, or a VPN you operate), never the raw public internet (§4). Multi-tenant rate-limiting is out of scope by design — a single-user localhost tool.
- **Rate abuse / network DoS on a personal loopback tool** — beyond the connection-admission cap (§4), a single-user localhost server has no multi-tenant rate-limiting, by design.
- **No TLS on the engine↔GUI and engine↔Ollama links.** Every call to an external service is TLS, and an API key travels only on those — measured: `src/` contains no plaintext `http://` to an external provider. The two plaintext links carry no API key; the one exception is `SERVE_AUTH_TOKEN` on a non-loopback bind. This is a scope decision premised on a private space — loopback, or a trusted private network you operate — and never the raw public internet.
- **No separation between the auth token and the session cookie.** The cookie carries the token itself (§4). Separating them needs a session table with expiry and revocation, and buys only per-device revocation — not worth it for a single-user tool on one or two devices. The cookie is therefore protected as the credential it is: `HttpOnly`, `SameSite=Strict`, constant-time compared.
- **No API versioning and no role separation (RBAC).** The engine and the UI ship as a version-matched pair and check it at `/api/health`. A tool with exactly one role has nothing to separate, and a `/v1/` in the path would be inventory to maintain rather than a control. A client holding the token can do everything the operator can — that is the single-user design, not a gap in it.

## 1. Integrity: Ensuring Data Consistency and Accuracy

To maintain the reliability of analysis results, a design based on a **Single Source of Truth (SOT)** is adopted.

#### ● Access Control via `TechnicalDataGuard` Struct

Operations on indicator data are controlled through the dedicated wrapper struct `TechnicalDataGuard`.

- **Restriction of direct access:** Direct read/write to internal data structures is restricted, forcing all access through the guard (wrapper). This structurally prevents unintended data overwrites and inconsistencies.
- **Limited interface:** Only the minimum necessary read/write interfaces for each process are provided, maintaining data integrity.

#### ● Access Boundaries Around Confirmed Data

Confirmed data is reached only through a validated path. Two boundaries carry this:

- **Technical (`TechnicalDataGuard`).** The wrapped entry is private; every write goes through a setter, and no API hands out a mutable reference to it. The guard also records **which indicators produced a value**: a setter marks its key only when it runs with a finite value, and a later failed recomputation clears both the value and the flag. So a value that was never produced — never computed, or a computation that failed — is **absent**, while a legitimately computed `0.0` is present; the distinction that matters for evaluation is "no value" versus "a real zero". This record covers the indicators held as a plain `f64` (RSI, MACD and its signal, the EMA/SMA legs, the band edges, %B), where `0.0` would otherwise be indistinguishable from nothing; the indicators already held as `Option` (ADX, %K, VWAP, ROC, Fibonacci, Ichimoku, volume) carry that distinction in the type. Rule and alert evaluation admits a value only when it exists in one of those two forms — an indicator that could not be calculated (too few bars for its period, or a failed evaluator) never arrives as 0.0, so a comparison such as `close > ema_l` cannot be satisfied by a value that was never produced. A condition referencing a missing indicator evaluates to false, which leaves the AND/OR combination rules unchanged. The backtest and the live alert monitor build that map through the same function, so both behave identically.
- **Fundamental (`FundamentalData`).** Fields are private and **every write path validates what it writes**, so a figure that has not passed the checks cannot be displayed, logged or sent to an LLM. The initial construction from a provider's result is concentrated in one path, which takes the in-flight `FundamentalInputs`; `Default` yields an empty value carrying no figures at all; and a later BPS or price update goes through a validated public method (`set_bps` / `recompute_derived`) that refreshes the ratios with it. The guarantee is not that there is a single entrance — it is that no entrance skips the checks. Non-finite figures are refused; a legitimate zero and a meaningful negative (a loss, a negative EPS) are kept. PER/PBR/ROE are derived **once, inside the confirmed data**, from validated inputs — not separately in each provider path and not per display path — and are recomputed whenever an input or the price changes, so a ratio cannot survive beside inputs that have moved on. The price a ratio came from is stored with it. A division that cannot be trusted yields no ratio at all — the field stays absent, never an infinity, a NaN or a stand-in zero. Refused are a zero denominator, a denominator so small it is indistinguishable from zero at `f64` precision (which would divide to a finite but astronomical figure), and any result that is not finite; a percentage is re-checked after the ×100, because a finite ratio can still overflow when scaled. Currency, unit, reporting period and source travel with the values; unknown information is left unknown rather than inferred.

#### ● Calculation Accuracy Through Combined Use of Proprietary Arithmetic and Standard Libraries

The following design is adopted to maintain the reliability of calculation results.

- **Single-execution calculation:** Each indicator calculation is performed only once per execution cycle. By sharing pre-calculated data, consistent values are provided regardless of output format (screen, log, LLM prompt, etc.).
- **Use of standard library `ta` crate:** The community-validated `ta` crate is adopted for basic indicators such as RSI, MACD, and EMA to ensure reproducibility.
- **Verification of proprietary arithmetic:** For indicators not provided by the `ta` crate or requiring specification-based adjustments (ADX, Stochastics, Fibonacci, VWAP, Ichimoku, etc.), arithmetic formulas are implemented with transparency ensured.
- **Handling error values:** In proprietary arithmetic, zero-division avoidance when the price range is zero (`high == low`) and rounding processing at judgment boundaries (eps) are implemented. This avoids numerical calculation failures and calculates safe alternative values (neutral scores, etc.).
- **Numerical checks:** `f64::is_finite()` finiteness checks and `clamp()` range constraints are applied during score calculation and weighting to prevent logic instability from extreme values.
- **Precision unification:** All internal calculations use `f64` to minimize precision loss from type conversions.
- **Data freshness management:** Acquisition logic that takes into account exchange update times outputs analysis results based on the latest market data.
- **Forecasting does not alter SOT:** Chat mode offers an opt-in forecasting capability (`/cast`). Integrity is preserved because the LLM never rewrites the computed confirmed values (prices, scores, indicator values); a forecast is a forward projection grounded on those values, labeled as a prediction and kept distinct from confirmed data. The values forming the basis of any forecast remain the ones computed by the program.

#### ● LLM Output Integrity Guard (numbers stay the program's job, not the model's)

The SOT boundary is enforced on the LLM's **output**, too. Every number in an analysis — indicator values, scores, prices — is computed in Rust; the LLM's only task is to **reason over and explain** those confirmed values, never to invent, unit-convert, re-derive, or compare them beyond the input. The prompt frame states this (prevention), and an output-side **integrity guard** catches what a model still slips through (detection + containment):

- **Why the guard is needed:** instructing a model not to fabricate reduces the risk but does not eliminate it — smaller / local models in particular still occasionally introduce a number the input never contained. Prevention alone is not integrity; the output must be verified against the input.
- **What it detects** — sentences/lines whose numbers do not belong to the confirmed data they claim: a figure attributed to the wrong symbol, the wrong indicator, the wrong unit, currency, magnitude, sign or point in time; a value with no confirmed counterpart at all; bare price ranges (`2600〜2700`); independently-derived buy/sell levels; out-of-input derived comparisons (industry averages, yields); and indicator readings stated in the **opposite** direction from the computed one (e.g. VWAP above the close when the confirmed VWAP is below it).
- **What it does** — it **surgically excludes only the offending sentences/lines** and keeps the rest (with a warning and a removed-character count); it is not a pass/fail score on the whole answer. Removal uses the **same sentence boundaries** the verification does, so in ordinary prose a correct sentence survives beside a wrong one in either language: "RSI is 45.2. The price is $999." keeps the first sentence exactly as its Japanese equivalent does. The granularity depends on what the line is: prose carrying more than one sentence loses only the offending sentences, while a **table row, a bullet or any single-sentence line is dropped whole** (a half-removed row would read as data it is not), and an alert's EXPLAIN note is **dropped in full** rather than trimmed — a one-line push has no room for a partial explanation. It is **model-agnostic** — keyed on API behaviour and on the input↔output comparison, never on model names — so it keeps working as models change (`--no-ollama-guard` / `OLLAMA_NO_GUARD` disables it; a `done_reason=length` truncation is still suppressed).

**Where the reference comes from — the structures, never the prompt.** The reference is built from the objects that own confirmed values — `TechnicalDataGuard` and `FundamentalData` — and is handed to the checker as data: symbol, name, currency, the bar the readings were computed on, the fiscal period the fundamentals belong to, and one entry per confirmed value with its indicator key, kind and own period. **No string is trusted as a source.** The prompt cannot be the reference, because the prompt also carries the conversation, the user's own turns and other models' opinions, and a label written by any of them is indistinguishable from one the engine wrote — a number a user typed would otherwise become "confirmed". Only indicators the guard records as actually computed become facts, so an indicator that failed to compute is absent rather than confirmed as 0.0.

The reference travels with the data it describes. **Every path that reaches an LLM carries it** — the CLI single analysis, every chat turn, `/basic`, `/forum` and the debate, the Web session, the Web multi-timeframe analysis (one entry per bar, each naming its timeframe) and the alert EXPLAIN note — and a reload replaces it together with the display text and the prompt context, so a refreshed value is accepted and the value it replaced is not.

**A number is read for what it is doing first.** Before anything is verified, each number is classified: an **observation** (a stated value), a **period parameter** (`RSI(14)`, `MACD(12,26,9)`, `14-day EMA`, `1時間足`, the `38.2` that names a Fibonacci level, the `1` in `1株あたり`) or a **date** (`2026-09-08`, `2019年`, `in 2019`). Only observations are claims about a value, so a window length, a level identifier, a per-unit basis and a date are never checked against an indicator — and a price that happens to look like a year (a close of 2025) is read as the price it is, because a year is only a year inside a date expression.

The parameter classes are **syntactic, not positional**: brackets are not an exemption. Only what is actually a period specification — whole numbers, optionally several of them, optionally with a unit of bars — is read as a parameter, so `RSI（99.99）` and `RSI (value: 99.99)` state readings and are verified. Likewise a Fibonacci ratio counts as a level identifier only where the writing marks it as one (`38.2%水準`, `38.2%:`), so an ordinary percentage stays an observation. And a figure carrying money or a unit is an amount whatever else its characters could spell: `$5m` is five million dollars, not a five-minute bar, so only a bare number can name a bar size.

**Spans are settled before the sentence is read, so notation does not change the verdict.** Where the numbers, the dates, the period specifications and the tickers are is decided in **one pass per sentence**, and every step that reads that sentence — the claim-splitting and all four bindings, for every figure in it — is handed that same result rather than re-deriving its own. This is what makes the following pairs agree rather than diverge:

- a **thousands separator** is punctuation of the figure, not the end of a claim, so `13,704,000,000,000` and `13704000000000` behave alike — including when the figure is reused under another fiscal year later in the sentence. The same holds for the commas inside `MACD(12,26,9)`;
- one **date** reads the same in every spelling — `2026-09-08`, `2026年9月8日`, `September 8, 2026`;
- a **full date** stamps when the observation was made and does **not** date the claim; only a year written *as* a year does (2019年, 年度, FY2025, "in 2019"). Naming the day an analysis ran therefore never refuses an annual figure whose fiscal year differs from the bar's, while a wrong value in that same sentence is still refused.

**A token is exempt only when it really is what it looks like.** The exemptions above remove figures from verification, so each one is recognised by its whole form rather than by a prefix:

- **month names** are the real ones, whole and anchored on both sides, inside an actual date construction. An open-ended reading also spells *margin* and *declined*, which would have exempted the number beside them;
- **the amount is the whole token**, magnitude included, whether the suffix is attached to the digits or written apart from them: `$168.8m`, `$168.8 m`, `$168.8mm` and `$168.8 million` are one amount, `$168.8bn` and `$168.8k` are others, and 百万 / 十億 read as their English counterparts do. A figure off by three or six orders of magnitude is refused exactly where the correctly scaled one is accepted;
- **a suffix the reader does not understand is never dropped.** A figure written in something the guard cannot check is not confirmed, because matching the digits and discarding the leftover would accept `$168.8x` as `$168.8`. An ordinal (`1st`, `3rd`) counts a position rather than a value and is not a reading at all.

**Detection algorithm — six checks, two axes.** Every check runs on the model's output against that reference. A check that does not fire leaves the sentence untouched.

**The checks are defined once, not per language.** Each row's vocabulary holds the Japanese and the English members of the *same* check, so a check cannot exist in one language only. Every row below applies to a `--lang en` answer exactly as it does to a Japanese one.

| # | Check | Fires when | Verified against confirmed data? | Catches |
| :-- | :--- | :--- | :--- | :--- |
| 1 | Number attribution | The output contains a number read as an **observation** | **Yes** — the number must match the confirmed fact its own sentence attributes it to, in symbol, indicator, unit, currency, magnitude, sign and point in time | A value moved to another indicator, symbol, timeframe, unit or period; a reading stated for an indicator that was never computed; a fabricated reading that carries no unit ("RSI is 99.99") |
| 2 | Numeric-unit expression | The output contains a number with a unit (兆円 / 億円 / 万円 / 円 / % / ％, or trillion / billion / million / yen / usd / dollars / percent / $¥€£) | **Yes** — a unit-carrying figure with no confirmed counterpart at all is reported here; misattribution is check 1's | Fabricated figures |
| 3 | Bare price / range | The output contains a number of 3+ digits whose value is ≥ 100 | **Yes** — same attribution test | Price levels the confirmed data never stated |
| 4 | Independently-derived buy/sell level | The output contains a trade-action word (エントリー / 利確 / 利益確定 / 損切り / 撤退, entry / take profit / stop loss / exit point …) **and** any number ≥ 100 | **No — by design** | Turning a number into a trade instruction |
| 5 | Out-of-input derived comparison | The output contains a term from a fixed list (業界平均 / 業界の平均 / 業界水準 / 平均的な水準 / 平均水準 / 同業平均 / 同業他社 / 配当利回り / 営業利益率 / 純利益率 / 利益率, plus 11 English equivalents) | **Yes** — passes if the input carries the same term | Fabricated **grounds** |
| 6 | Contradicting indicator reading | The output states a VWAP direction opposite to the computed one, in either language | **Yes** — the direction is read from the confirmed VWAP and close, so the prompt's label wording cannot change the verdict | Explanations that invert the computed reading |

**What "verified" means for a number.** A match requires the value *and* its attribution, decided **per claim** rather than per answer. One sentence often carries several claims — 「日足の終値は168.8円、1時間足の終値は170.2円」, "revenue was X in FY2025 and Y in FY2024" — so each qualifier is bound to the claim it was written in. Claims are separated at 、 , ; and at *and* / *while* / *whereas* / *but*, which reads a qualifier written **before** the figure (Japanese) and **after** it (English) alike. Sentence boundaries are read in both languages too: an English `.` ends a sentence only when whitespace or the end follows it, so neither a decimal point nor a ticker's dot merges two claims.

- **Which instrument** — the one named in the same claim, so "AAPL is $168.8 while MSFT is $400" attributes each figure to its own issuer and the pair with the values exchanged is refused. A code that is also an ordinary word (`IT`) or a single letter (`A`, `T`) is still this session's instrument when it is loaded: known symbols are matched before any ordinary-word filter.
- **Which timeframe** — where one instrument is loaded on several bars, the bar named in the claim selects that bar's values; the daily value is not accepted as the hourly one, and a bar that was never analysed carries no value at all.
- **Which indicator** — the one named in the claim, and a name counts only when it stands **as a word**: `ema` inside "remains" and `per` inside "period" are not mentions, and binding a figure to an indicator found that way would attribute it to something the sentence never named. The boundary is against letters rather than characters, so a Japanese sentence that runs the value straight onto the name (`VWAP168.96`) still binds, and an English plural ("prices", "bands") still counts. Generic wording is recognised beside specific wording, so "RSI is 45.2 and EMA is 166.88" binds each figure to its own indicator. A reading offered for an indicator with **no confirmed value at all** is refused rather than passing unexamined.
- **Which leg** — two legs of one indicator differ only by the window they were computed over, so the window travels with the value and a sentence that names one is held to the leg it names. An unqualified name ("EMA") may cite either leg; "long EMA" may not cite the short one; on a daily analysis `EMA(20)`, `EMA(20 days)`, `EMA（20日）`, `20日EMA` and `The 20-day EMA` are one statement, and on a monthly one `EMA(20 months)` and `The 20-month EMA` are — the reader that *excludes* a window from verification and the reader that *uses* it to pick a leg take their vocabulary from one definition, so no spelling of a window is understood by only one of them. A window that was never computed (`The 25-day EMA`) carries nothing and is refused. **What is compared is the number, not the unit:** the engine holds one window per leg (a period count, whose meaning is the analysis timeframe), so `The 20-month EMA` written during a daily analysis is accepted as the 20-period leg. Checking a stated time unit against the analysis timeframe is not implemented. The window applies to the indicator it was written on, so `RSI(14)` in "RSI(14) is 45.2 and EMA is 166.88" does not select a leg of the EMA beside it — and an indicator the engine does not track per window (RSI) is never refused for carrying one.
- **Unit, currency and magnitude** — the currency prefix, the magnitude word and the trailing currency word are read as one expression, so `13704 billion dollars` is a dollar figure and not a yen one. A magnitude is a **scale only**: 万/億/兆 and million/billion do not by themselves make a figure money, so a share count may be written "12 million" and may not be written "$12 million". A currency may only be written on an amount, so `$45.2` is refused as an RSI reading and `Volume is $1000` is refused as a share count.
- **Precision** — rounding is judged at the magnitude the number was written in: a confirmed 13.704兆円 may be written 約13.7兆円, and 13.8兆円 may not; 168.8 stands for a confirmed 168.80, and 168.9 does not. Sign must match, and it may stand on either side of a currency symbol — `-$2.50` and `$-2.50` are the same amount, and both are refused against a confirmed `+2.50`. Thousands separators and full-width digits are normalised first.
- **Period** — a technical reading is checked against the bar's year and a fundamental one against its own fiscal year, so stating the fiscal year of an annual figure is not refused because the bar is from another year. Only a year written **as** a year counts (2019年, 年度, FY2025, "in 2019"); a full calendar date stamps when the analysis ran and does not date the claim.
- **A condition the engine itself stated** — an alert reports the rule that fired (`score <= 5`), so that condition is part of what the engine told the model and may be restated. The comparison in the sentence is **parsed**, not inferred from a word occurring somewhere, and the parsed indicator, direction, equality and value must all match the rule: `score >= 5` and `score < 5` are different rules and are refused, and so is `score <= 5` where the rule said 5.4 — display rounding may change a reading's last digit, never a condition. The number must be written as the rule wrote it, bare: `score <= $5`, `score <= 5%` and `score <= 5foo` state something the rule does not. Recognising a comparison and accepting it are separate steps — a unit on the threshold makes the condition unacceptable, not un-recognised, so it is refused **as a condition** rather than handed back to the reading check, where `close > ¥3091` would have passed on an instrument whose close is 3091. Both languages are read the same way, the comparison standing before the number in English (`at or below 5`) or after it in Japanese (`5以下`). The operator qualifies **the number it compares** — the one that follows it with nothing but space between — so in "score is at or below 5 (current value: 0.0)" the 5 is the rule and the 0.0 is a reading, each checked as what it is. A sentence that states the indicator *is* that number ("the score is 5") is not a restatement and stays a fabrication. And once a sentence writes a condition on an indicator the engine stated a rule for, it is judged **as a condition**: a wrong direction is refused even where the threshold happens to equal the current value, which the reading check would otherwise have accepted.

Numbers that exist only in the conversation history, in a user turn or inside another model's opinion **cannot** become confirmed data — not because such lines are filtered out, but because no text is ever read as a source: the reference comes from the guard and the fundamental data alone.

**Limitations, stated rather than assumed away.**

- Two paths run **without** confirmed data, and each says what it does check instead:
  - **free-form conversation with no instrument loaded** — nothing has been computed, so there is nothing to attribute against;
  - **news triage** (`/news` filtering) — the task is to sort the titles the model was given, so its numbers must come from those titles, not from the market data. Passing the instrument's confirmed values here would refuse a figure quoted correctly out of a headline.

  On both the guard falls back to the older presence test — the number must occur in the input it was given — and does **not** claim the attribution was verified. Everywhere else the confirmed data travels with the request, the Ollama benchmark included: it runs the analysis prompt, so each model's row is scored against the same confirmed values the analysis itself is.
- A **bare uppercase symbol** (`MSFT`) is read as naming an instrument only in a session whose own instruments are written that way, only from two characters up, and only when it is neither part of the guard's own vocabulary nor an enumerated ordinary word or acronym (`I`, `IT`, `AI`, `CEO` …). A bare foreign US symbol quoted inside a Japanese-listing session is therefore not flagged as foreign — its number is still verified against the confirmed values. The alternative, reading every uppercase token as a symbol, drops legitimate sentences ("I see RSI at 45.2").
- When the provider reports **no currency** (the labelled Stooq fallback), a written currency is not refused: an unknown cannot contradict it, and refusing would assert knowledge the engine does not have. The value itself is still verified.
- The term list in check 5 is a fixed enumeration, not exhaustive coverage.

Checks 1, 2, 3, 4 and 6 police **fabricated numbers**; check 5 polices **fabricated grounds** — a basis xoksa cannot verify. Check 4 deliberately skips the comparison: a figure that *is* confirmed still becomes something the data never said once it is presented as an entry or exit level, so this check reads the number's **use**, not its origin. Check 5 being a list comparison means the term passes when the input genuinely carries it — for an issuer whose fundamentals block states 営業利益率, the model may use that word.

**What is deliberately not detected.** A forward-looking statement is not an integrity violation. A sentence such as 「この勢いなら年内に急騰します」 carries no number, no price level and no external basis, so no check fires and it is displayed. Asking a model for a view means accepting that the view contains inference; what the guard removes is fabricated figures and unverifiable grounds, not inference itself. Forecasts are handled separately, labelled non-SOT (see "Forecasting does not alter SOT" above). A vague basis phrased outside check 5's list ("generally", "across the market") passes.

**A detection is not a demerit.** The issue count is not a quality score for a model. The opportunity to detect grows with how much specific content an answer contains, and falls to zero for an answer that states nothing — so the count is meaningless on its own and must be read together with the volume of output.


**Why this matters — small, local models become usable.** Because the arithmetic is handled by deterministic code, the model is freed to spend its capacity on *interpretation* rather than on recalling or converting numbers. That division of labour is precisely what lets even a relatively **small, local (Ollama) model** produce genuinely useful analysis — and the integrity guard is the safety net that makes trusting a weaker model's output safe, because its numbers are never the ones relied upon. The result: private, low-cost, offline inference **without** surrendering numerical trustworthiness.

## 2. Confidentiality: Protection of Sensitive Data

Thorough protection of sensitive information such as API keys and user environments is implemented.

#### ● Design as a Member of the OS (Leveraging Rust)

- **Memory safety:** Rust's type system and ownership model prevent memory leaks and segmentation errors in advance. Implements safe use of system resources without adversely affecting other processes.
- **Thorough boundary sanitization:** External inputs such as ticker symbols, news queries, and file paths are subject to permitted character restrictions (alphanumeric restrictions, etc.) and removal of control characters (semicolons, pipes, etc.), reducing the risk of injection attacks. Dynamic identifiers (timeframe, indicator name) are restricted to known values (`AnalysisMode` tokens / a fixed indicator set), never taken verbatim from input.
- **File path resolution:** Path normalization and existence checks are performed for all file accesses. Structurally defends against writes and reads to unintended directories.

#### ● API Key Management and Disposal

API keys are important assets, and the design minimizes their exposure time.

- **On-demand deployment:** API keys are not kept in memory constantly but are obtained only immediately before building a request.
- **Zeroize on disposal:** Memory areas containing used API keys are immediately cleared with the `zeroize` crate, zeroing out the key material in memory. This prevents key information leakage from unexpected memory dumps or traces.
- **Structural blocking of exposure:** Mask processing is thoroughly applied so that API keys are not exposed from debug output, logs, or internal structures.

#### ● Software Supply Chain Transparency

#### Supply Chain Risk Reduction (`cargo audit` + `cargo deny`)

To manage the risk of known vulnerabilities lurking in dependent libraries, scanning using the RustSec advisory database is incorporated into the development process.

- **Continuous verification**: `cargo audit` is run against all dependent libraries on every push, maintaining a response system when vulnerabilities are reported. `cargo deny` runs beside it on the same trigger, covering what an advisory scan does not: **licence and source compliance**. A new transitive dependency can arrive under a licence the allowlist has never been asked about, which is a release-blocking fact that no test or lint reports. `cargo machete` prunes unused dependencies on the same run.
- **Publication of scan results**: per-release SCA results, bound to each artifact's hash, are recorded in the [shipping inspection](./security-assessment.md).

#### SBOM (Software Bill of Materials) Provision

- A **CycloneDX 1.5** SBOM is published under [`sbom/`](../../sbom/), one per shipped artifact target: `xoksa-native-windows-x86_64.cdx.json` and `xoksa-native-macos-arm64.cdx.json` (the shipped engine, default `embedded-ui`), `xoksa-desktop-windows-x86_64.cdx.json` and `xoksa-setup-windows-x86_64.cdx.json` (the shipped desktop shell and settings app of §6, Tauri/WebView2), plus `xoksa-webui-leptos.cdx.json` (the WASM frontend, host-independent). Per-OS is required because an SBOM lists what is *in that binary* — the platform crates swap out (`schannel` / `windows-native-keyring-store` vs `security-framework` / `apple-native-keyring-store`) even though the `Cargo.lock` is identical. This gives every used component a machine-readable inventory that SCA tooling can ingest. (The desktop app and the settings app are separate workspaces with their own lockfiles, so a root build never covers them; each carries its own inventory, regenerated by the same throwaway `cargo auditable` method.)
- Generated with **`syft`** at CycloneDX spec 1.5, regenerated per release (the inventory is version-specific). The native inventories are read from a throwaway `cargo auditable` build — the dependency list embedded in the binary itself, not the lockfile — so they list what is in *that* artifact; the WASM frontend is catalogued from its own `Cargo.lock`, which resolves for `wasm32-unknown-unknown` only. `cargo-cyclonedx` is **not** used: it writes an absolute workspace path into `bom-ref` with no way to suppress it, and post-editing tool output is rejected on principle. See [`sbom/README.md`](../../sbom/README.md) for the exact commands and the host-target caveat.

#### How to Configure API Keys

The recommended API key storage method is the OS Keychain (macOS Keychain / Linux Secret Service / Windows Credential Manager) via `--init` or `--update-key`. Each key occupies its own Keychain entry (`Entry("xoksa", "<KEY_NAME>")`). This is the preferred configuration because it avoids keeping API keys as cleartext in the project configuration file while preserving on-demand retrieval and zeroization in the application code.

For users who prefer conventional CLI operation, need simple local setup, or want to avoid OS authentication dialogs, `xoksa.env` based API key configuration remains supported. If a key is present in `xoksa.env`, the `xoksa.env` value takes priority over the Keychain entry. When using `xoksa.env`, the user is responsible for protecting the file with appropriate filesystem permissions. Values loaded from `xoksa.env` must still cross the loader boundary as `Zeroizing<T>` and must not be stored in `env_map` or `Config`.

Specifying API keys via command line arguments is not supported. This is a design decision to eliminate the risk of exposure in command history or process lists.

## 3. Availability: Robust System Execution

Design for continuing analysis processing even in unforeseen circumstances.

#### ● Robust Error Handling (Robustness)

- **`unwrap` / `expect` policy (keyed on reachability, not a blanket ban):** They are **not used on values derived from untrusted or external input** — network responses, config / environment, user input, or parsing of untrusted data — because a panic on a path reachable from such input is a crash, i.e. an availability / DoS risk; those paths use `?`, `match`, or graceful continuation instead. They **are** used where the value is provably present — a same-scope check, a type / module invariant, or a compile-time constant (e.g. a static `LazyLock` regex validated at build with `.expect("valid regex")`) — with `expect("why it cannot fail")` documenting the invariant. Over-defensive error handling for cases that cannot occur is avoided, since it obscures intent and makes an impossible failure look reachable.
- **Resilience:** By defining safe default behavior for API response delays and configuration deficiencies, availability is maintained without hindering the user's analysis work.
- **Server & provider availability (cross-refs):** for the local server, request admission is capped and one slow chat turn cannot stall other endpoints (§4); for external data, provider **failover** (Yahoo → labelled Stooq), timeouts, and graceful degradation are covered in [security-assessment.md](./security-assessment.md). Values are never fabricated to fill a provider gap.

## 4. Local server (`xoksa serve`) security model

The browser dashboard is served by the binary's **own embedded HTTP server (axum)** — no Apache/nginx, no separate application server, no language runtime. The design-level controls are below; the point-in-time review, the verified-safe classes, and the penetration-testing playbook that exercise them live in [**security-assessment.md**](./security-assessment.md).

**Loopback by default.** The server binds `127.0.0.1` for local use. The realistic attacker here is a **malicious page open in the same browser** (drive-by CSRF against `localhost`) and **malicious upstream data** (news titles/URLs, market feeds). Any non-loopback bind (`--host 0.0.0.0`) widens the surface beyond the OS trust boundary, so it is **fail-closed** (see next).

**Non-loopback binding is fail-closed and token-gated (remote / distributed use on a trusted private network).** The engine and UI are split by design, so the engine may run on another machine and be queried remotely. A non-loopback bind (`--host 0.0.0.0`, or the desktop `DESKTOP_LAN_ACCESS` toggle) **always runs with an auth token active** — if none exists yet, the engine **auto-generates a 256-bit token (OS RNG, unguessable)** on first non-loopback start, so a non-loopback server can never run unauthenticated. The token is a **credential-grade secret** (OS keyring, `Zeroizing`, never a process argument or a log line). Because the operator does not choose it, the engine **shows it on demand** — printed once at generation and re-shown via `xoksa serve --show-token` — so a remote client can be configured; this is a documented exception to the credential never-display rule (§0.1), safe because the operator is inside the OS trust boundary, and the token is rotatable via `--rotate-serve-token`. Every request to a non-loopback-bound server must present it — as an `Authorization: Bearer <token>` header (CLI / API / a future REST client), or a browser posts it once to `/auth` and is handed back an `HttpOnly` / `SameSite=Strict` cookie (`xoksa_auth`) that **carries the token itself**, compared in constant time on every later request. *(Corrected 2026-10-01: this said the browser "exchanges it for a session cookie", which describes a separate session value this server does not mint. Keeping the two the same is a deliberate choice — a session table buys per-device revocation, which a one- or two-device tool does not need — so the cookie is protected as the credential it is: `HttpOnly` keeps it away from script, `SameSite=Strict` from cross-site sends.)* **In addition, only private/loopback source addresses are accepted** — a private-range / loopback check on the connection's source — so a non-loopback-bound server answers only within the local network, **never the raw public internet**; remote use is kept **inside a trusted private network** (a LAN, or a VPN you operate).

**Per-client session isolation (confidentiality + integrity).** Each browser is issued a random `xoksa_sid` cookie (32 hex chars, `HttpOnly`, `SameSite=Strict`); Web session state is namespaced by that id — keyed `sid|symbol|timeframe` — so **one client can never read or mutate another's session**. `HttpOnly` keeps the id unreadable by any script (an XSS cannot steal it); `SameSite=Strict` blocks cross-site cookie send. No `Secure` flag, because the loopback default is plain `http`.

**Browser-attack-surface hardening (defense-in-depth).** Output-encoding is the primary XSS defense — all user/external strings render as escaped text or through the HTML-escape helper, never raw `innerHTML`, and news URLs are scheme-checked (`javascript:` blocked). On top of that, every response carries a **strict, nonce-based Content-Security-Policy** with no `'unsafe-inline'` (`default-src 'self'`; `connect-src 'self'` blocks exfiltration; `object-src`/`base-uri`/`frame-ancestors 'none'`; `form-action 'self'`), a **Permissions-Policy** denying geolocation/camera/microphone/payment/USB/motion sensors, plus `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`.

**Request policy.** State-changing POSTs use axum's `Json<T>` extractor, which enforces `Content-Type: application/json` — a cross-origin `application/json` POST triggers a CORS preflight the server never answers, and a `text/plain` request is rejected `415`. Those routes additionally carry a server-side origin check, and the `GET`/SSE chat endpoint — the one path a preflight cannot cover — carries an explicit same-origin check. A global request-body-size limit and a cap on saved backtest rules bound resource use; the saved-rules path is fixed (no path injection from a rule name).

**Availability (self-DoS resistance).** A connection-admission semaphore admits at most **256 requests at once** and sheds the rest with `503` rather than queuing unboundedly. The figure is stated because a cap only bounds what it is smaller than: an earlier `65535` would have let the host's own RAM and file descriptors run out first, which is not a `503`. A browser holds six connections per host, so 256 is some forty tabs' worth of a single-user tool. A permit is released when the handler returns its response — **a live SSE stream therefore holds none**, and a long chat does not occupy the pool — so what a permit is held for is one handler, bounded by the outbound client timeout, whose own ceiling is capped (15 minutes) so that a configured value cannot extend the hold without limit. Web sessions sit behind **per-session** locks — never a single global lock held across an LLM stream — so one slow chat turn cannot stall unrelated endpoints such as the symbol summary.

**Secrets never cross the browser boundary.** API keys stay in the OS keyring and are zeroized; the JSON API reports only key **presence**, never values. No credential is ever sent to the browser. **This HTTP boundary is unchanged by the desktop app:** the axum server never receives an API key. The **settings app** submits keys over the **Tauri IPC** boundary (local, never over HTTP), then forwards them to the engine over the child process's stdin (`xoksa apply-config`); the key transits only the local WebView's JS context, the IPC channel, and the engine's stdin, and is handled as `Zeroizing<T>` on the Rust side (see §6).

> **The aim is to verify security, not just declare it.** The goal is to inspect every release against the *exact* binary users download — a documented shipping inspection, including the web-server penetration tests above — with each check measured on that binary's hash. The static review and the dynamic-testing playbook are in [**security-assessment.md**](./security-assessment.md); the per-release results are recorded in the [**shipping inspection**](./security-assessment.md).

#### ● Chat notification (push) — outbound only to a fixed per-platform host allowlist

A background monitor task inside `xoksa serve` — one task for the whole process, running only while `serve` is up, with no background residency and no dependency on an open dashboard — watches the intraday bars at their own cadence and, when a user-defined condition on a **computed value** is met (e.g. RSI ≤ 30), pushes a one-line notification to a chat platform (Slack / Discord / Google Chat via an incoming webhook; LINE via the Messaging API). The bar it evaluates is the latest bar of the series — on Japanese intraday timeframes that is the still-forming bar carrying the real-time quote, so a crossing can be caught within the bar rather than only after it closes. This is decision-support, not action — the message carries the **computed (SOT) fact** (ticker, bar time, the indicator value that crossed, the threshold), never an LLM-authored trade call; an optional short explanation, when enabled, still passes the §1 output-integrity guard. What it watches comes from the rules, not from any session: each rule carries its own ticker, and the monitor fetches and recomputes that ticker itself. No browser, no open tab and no particular symbol on screen is required; only stopping `serve` stops it. Rules are read from `xoksa.env` once, at startup — a change made through the dashboard or `/alert` takes effect at once and is written back, while a hand edit of the file takes effect on the next start.

The path is constrained:

- **Fixed outbound hosts.** The destination host is a hardcoded per-platform allowlist — `hooks.slack.com` / `discord.com` + `discordapp.com` / `chat.googleapis.com` / `api.line.me` — validated `https`-only. The user supplies only the non-host secret (the webhook token/path, or the LINE bot token + destination id); a URL whose host is not on the allowlist is rejected. So §4's anti-SSRF property — outbound hosts are fixed in code, never taken from input — is preserved.
- **Secret is credential-grade.** `NOTIFY_<n>_SECRET` (webhook token/path or bot token) grants posting to the user's channel; it lives in the OS keyring, is handled as `Zeroizing<T>`, and is never logged, never a process argument, never sent to the browser. It is registered like an API key (`--update-key`, or the desktop settings app over the child's stdin), not via a chat command.
- **Data POST only.** The notifier `https`-POSTs the message; it never runs a shell and never executes an arbitrary command or endpoint on a signal (a notification is a data hand-off, not an action trigger).
- **Rate control.** A crossing fires once per (ticker, condition, indicator bar) on a rising edge — not on every poll, and not again while the condition simply stays true.
- **A failed send is visible, not silent.** A send is attempted once — the monitor swallows the failure so one bad channel cannot stop it, and it does not retry — so the outcome of the last attempt (time, success or failure, and the reason) is held per rule and shown in the dashboard's alert panel. Without it a rule that fired and failed to deliver is indistinguishable from one that never fired. The reason carries no secret: the notifier rebuilds its failure text without the URL and redacts the secret from it (§0.1), which is what lets the text be displayed at all.
- **`--private` honored** — no notification, URL, or secret is written in a no-trace session.

## 5. Distribution integrity & anti-malware false positives

The **CLI / server binary (`xoksa`)** is an unsigned native binary that binds a loopback HTTP server, makes outbound HTTPS calls (LLM / market / news), and reads the OS keyring for API keys. That legitimate combination (network + credential-store access) is exactly what behavioral AV/ML engines score as suspicious, so a **false positive** on Defender / VirusTotal is a realistic risk even though this binary contains **none** of the classic malware markers:

- No process spawning or shell-out (`std::process::Command` is not used in the analysis / CLI / server binary).
- No `unsafe` (compiler-enforced via `#![forbid(unsafe_code)]`), no Win32/`winapi`/`LoadLibrary`/`VirtualAlloc`/`GetProcAddress`.
- No registry writes and **no self-persistence** — the binary installs no autostart entry and writes no registry key; no packing/obfuscation. The one embedded asset — the WASM UI (via `include_dir!`) — is a legitimate application resource compiled into the read-only `.rdata` section, **not** the `.rsrc` icon section that behavioural ML engines score for entropy (the shipped engine's `.rdata` measures ~5.9 at 2.9.9; the v2.6.8 engine measured ~6.16 and scanned 0/69, which is the datapoint the case study rests on — see [av-false-positive-case-study.md](./av-false-positive-case-study.md)). *Scope: this is a property of the binaries. The optional Windows **installer** (§6) necessarily registers a standard uninstall entry under `…\CurrentVersion\Uninstall`, as every MSI does — that is the OS's uninstall contract, not application persistence: nothing autostarts, and uninstalling removes the entry.*
> **The desktop app (Tauri, §6) is a separate binary with a different profile** — it hosts an OS WebView and spawns the `xoksa` engine as a child process. Its anti-FP and signing posture is covered in §6, not by the bullets above.

**Hardening checklist (release engineering):**
1. **Code signing (Authenticode, ideally EV)** — the industry's definitive fix, and an immediate SmartScreen-reputation grant. macOS artifacts are signed + notarized; the Windows artifacts currently ship unsigned and control false positives at the build level instead (below, and §6).
2. **Ship and scan the release build only.** The `release` profile is hardened (`strip = true`, `lto = true`, `codegen-units = 1`) → a small, symbol-free binary. Debug builds (strings, paths, panic text, unoptimized) are far more FP-prone and must never be distributed or scanned.
3. **Reproducible build + published SHA-256** so users can verify the artifact matches source.
4. **False-positive submission** to Microsoft (and a VirusTotal rescan) when a detection appears; reputation also accrues with signing + download volume.
5. Keyring (credential-store) access is a real feature and is kept; it is documented here as a known behavioral signal, not removed.

**AV false positives — addressed in the build, not by signing.** The shipped desktop icon is constrained to uncompressed BMP frames (max 64×64) to keep the PE resource section small and low-entropy, which is what the behavioural ML engines score; the method and the reproducible experiment matrix are in [**av-false-positive-case-study.md**](./av-false-positive-case-study.md). A clean multi-engine scan is not an audit, and a first-scan flag on a new hash can be reputation rather than content — per-release scan results, bound to each artifact's hash, are recorded in the [shipping inspection](./security-assessment.md).

## 6. Desktop app (Tauri) security model

Two **Tauri UI shells** lower the barrier for non-CLI users, and neither links any engine code — each launches the `xoksa` engine binary shipped beside it as a **child process**. The **desktop app** is a connection shell: it asks *which engine to talk to* (a local engine it auto-starts via `xoksa serve`, or a remote one by address + access token), then points an OS WebView at that engine's dashboard. The **settings app (`xoksa-setup`)** is a separate standalone app where all configuration lives — API keys, LLM / indicators / news / notify, the serve access token, and a settings password — password-gated and opened from the desktop's **Settings**. The analysis engine, SOT, and all §4 server controls are the engine's, reused unchanged; the CLI and `serve --ui` are unaffected. The desktop drives `serve`; the settings app drives the config / keychain subcommands (`config-json` / `apply-config` / `settings-password` / `conn-token` / `ollama-models` / `test-notify` / `serve --show-token`·`--rotate-serve-token`) and may **restart the engine** (`serve --ui`) — a change to the access token or the port only takes effect on a fresh engine, so the app that sets them is the app that must be able to cycle it. It is one action: with nothing running it starts the engine, and it refuses (naming the port) when a process it did not start already holds that port — this app never kills a process it did not spawn. The port itself (`SERVE_PORT`, default 8787) is a visible setting on the same card, not an env-file-only value. That engine **outlives the settings app**: the settings app is transient (it is opened to change something and closed again), and tying the engine's life to it would drop the connection the operator just configured. This is the deliberate difference from the desktop, whose auto-started engine is killed with its window. This section states the security commitments specific to these builds; they are **design contracts** the implementation must satisfy.

**Distinct binaries, distinct profile.** The desktop app and the settings app are separate artifacts from the CLI/server binary (§5). Each hosts an OS WebView (Windows WebView2 / macOS WKWebView / Linux WebKitGTK) and spawns the `xoksa` engine as a child process. That child-process spawn (which the CLI never does) plus config + keychain access raise the behavioral-AV signal surface beyond §5's markers; their false-positive controls and per-OS signing status are covered below.

**Process launch uses no shell.** Every process either app spawns — the `xoksa` engine (the desktop: `serve`; the settings app: `config-json` / `apply-config` / `settings-password` / `conn-token` / `ollama-models` / `test-notify`, plus `serve --ui` for its start/restart), the desktop launching the settings app, and the OS "open URL in the default browser" handler — goes through `std::process::Command` with an explicit argument vector, **never a shell**, so no argument can inject a command. The engine's path is resolved from the app's own executable location (the binary shipped beside it), never from the WebView. Arguments are chosen in Rust; the only WebView-derived values are the Ollama host/port for `ollama-models` (Class B, non-secret) and the external URL to open (validated to an `http`/`https` scheme), each passed as a separate `argv` element, never interpolated into a string. Arbitrary shell execution is never exposed to the WebView/JS layer.

**API keys reach the keychain over local channels only — never the HTTP server.** The **settings app** collects API keys (Class A) and passes them over the **Tauri IPC** boundary to its Rust command, which forwards them to the engine as a JSON payload on the **child process's stdin** (`xoksa apply-config`); the engine writes them to the OS keyring (`keystore::set_key`). The axum HTTP server never receives a key (§4 unchanged), and **no key is ever a process argument**. A key transits only the local WebView's JS context (no remote origin; CSP-locked), the Tauri IPC channel, and the engine's stdin pipe; the settings app zeroizes its JSON buffer after the write and the engine handles keys as `Zeroizing<T>` (§2). `apply-config` reuses the same headless apply-setup logic as `--init` (env-file + keychain write), so all paths write identically. The settings app's **channel test** takes the same route: `xoksa test-notify` receives the typed channel secret on the child's stdin (never argv), so a channel can be verified before it is saved and the secret still never touches a process argument, the HTTP boundary, or a log.

**Least-privilege capabilities.** Each app's Tauri capabilities are restricted to exactly what it needs: the desktop's connection commands and the settings app's configuration commands on their local app origins, and — for the desktop's loopback dashboard origin — only the window-popup and external-link commands plus the event channel. No broad filesystem, no arbitrary `shell`, no arbitrary `http` capability is granted to either WebView.

**Single, stable config location (SOT).** `xoksa.env` resolves to ONE canonical, user-scoped path — `<config_dir>/xoksa/xoksa.env` (Windows `%APPDATA%\xoksa`, macOS `~/Library/Application Support/xoksa`, Linux `~/.config/xoksa`) — shared by the CLI, `serve`, and the desktop, independent of the working directory, and shared by the settings app too. Resolution is simply `--env-file <path>` > the canonical path; there is **no** implicit `./xoksa.env` fallback, so the config cannot split by launch directory. On startup a **one-time, non-destructive migration** imports an existing config into the canonical location — first a pre-2.7.1 desktop config (`<data_dir>/app.xoksa.desktop/xoksa.env`), else a working-directory `./xoksa.env` — by copying it (never overwriting an existing canonical file), so upgrades keep their settings. The canonical directory is defined once in the shared `xoksa-paths` crate (depended on by the engine, the desktop, and the settings app, so it cannot drift); the engine resolves the file in one place (`utils::env_path`). `--private` (no-trace) semantics are preserved.

**Signing.** macOS desktop and settings-app artifacts are Developer ID–signed and notarized. Windows artifacts currently ship unsigned; every artifact carries a published SHA-256 and a shipping-inspection record, so it is verifiable without a signature.

**Local auto-start never adopts a foreign engine.** When the desktop auto-starts a loopback engine, it asks the OS for an ephemeral port (bind `:0`, read, release) instead of a fixed one, so the child can never contend with a stale `xoksa serve` or any foreign process, and multiple app instances coexist — each with its own engine. Before the WebView attaches, the engine must answer `/api/health` as `xoksa-web` reporting **exactly this app's version** (the desktop and engine ship as a matched pair); the desktop connects only to the child it spawned. When LAN access is on (§4, fail-closed), the engine keeps the fixed, user-known port that remote devices rely on — that port is probed before spawning, and an occupied port is refused with the occupant named. Every auto-start failure is reported with its cause (spawn failure, immediate child exit with its status, port occupancy and by what, HTTP 401 distinguished from unreachable, timeout with the last observed state) — never a bare timeout. The ephemeral port is never persisted.

**LAN exposure is opt-in and defaults off.** The desktop binds the engine to loopback (`127.0.0.1`) by default. The settings app's `DESKTOP_LAN_ACCESS` toggle is the only path by which the GUI binds `0.0.0.0`; as in §4 that non-loopback bind is **fail-closed — it requires an auth token or the engine refuses to start**, accepts only private/loopback source addresses, and safe remote use is kept **inside a trusted private network**, never the raw public internet. The same capability is available on the CLI as `xoksa serve --host 0.0.0.0`.

## 0. シフトレフト・セキュリティ（目指す設計）

**本プロジェクトは、セキュリティを後付けの制約ではなく設計判断の出発点に置くことを目指す。**

本プロジェクトはシフトレフト・セキュリティの姿勢を目指す。人間・AIを問わず、貢献者は以下の原則に沿うよう努める。

> **セキュリティは設計にとどめず、出荷する現物バイナリに対して検証することを目指す**——各リリースを点検し、その結果をバイナリのハッシュに紐づけることを目標とする。Web サーバの serve モード設計コントロールは §4。時点の脆弱性診断（所見・検証済み SAFE クラス・ペネトレーションテストの playbook）と、出荷バイナリのハッシュへの紐づけは [**security-assessment.md**](./security-assessment.md) に記録する。

- **セキュリティを設計の起点とすること**: APIキー・認証情報・外部入力・機密データに関わるコードを書く前に、本ドキュメントを確認し、設計が整合するよう努める。実装は設計に従う。設計が実装に引きずられてはならない。
- **後付けセキュリティを避ける**: 動作するコードにセキュリティを後から足すことは避けることを目指す。「動くが安全でない」状態を、許容できる到達点とはみなさない。
- **実装前の資産特定**: データを扱うコードを書く前に、そのコードが生成・保管・送受信・処理するすべての情報資産を列挙する。各資産について Section 0.1 の特定基準を適用する。特定されていない資産にセキュリティ対策を当てることはできない。
- **セキュリティ違反を重く扱う**: 監査で見つかった違反は、可能な限り後回しにせずブロッキング欠陥として扱うことを目指す。「動く」という事実だけでは修正を先送りする根拠にならない。

これらの原則は、新機能・リファクタリング・差分変更を問わず、すべての変更に適用される。判断に迷う場合は、実装を進める前に本ドキュメントで確認すること。

**言語同期ルール：** 英語セクションと日本語セクションはどちらも規範である。セキュリティ要件は両言語セクションの和集合として解釈する。片方の言語にだけ要件・例外・制約が記載されている場合でも、その要件は有効であり、欠落している側を更新しなければならない。この不一致はセキュリティポリシーの変更ではなく、ドキュメント不備として扱う。

## 0.1 保護対象資産の特定

このプロジェクトが扱う資産は、性質の近いものを2種別に整理する。

- **プライベートデータ**: ユーザーの認証情報・環境・ネットワーク構成に関するデータ。例: APIキー、パスワード、認証トークン、OllamaサーバのIPアドレス。
- **パブリックデータ**: 公開情報源から取得・算出されるデータ。例: 株価、算出済みテクニカル指標、ファンダメンタルデータ、ニュース記事。

各種別のセキュリティ要件は、CIAトライアドの3観点で影響を評価することで導出する。

- **機密性（Confidentiality）**: 露出した場合に被害を招くか
- **完全性（Integrity）**: 改ざんや汚染が被害を招くか
- **可用性（Availability）**: アクセス不能になった場合に被害を招くか

各資産に割り当てる保護クラスは、この3次元評価を反映している。実装のテクニックはセクション1（完全性）・セクション2（機密性）・セクション3（可用性）に記載する。

以下の表は、各資産の種別と保護要件をまとめたものである。

### クラス A — 認証情報（完全な保護が必要）

| 資産 | 説明 |
| :--- | :--- |
| `OPENAI_API_KEY` | OpenAI APIキー |
| `GEMINI_API_KEY` | Google Gemini APIキー |
| `CLAUDE_API_KEY` | Anthropic Claude APIキー |
| `BRAVE_API_KEY` | Brave Search APIキー |
| `JQUANTS_API_KEY` | J-Quants APIキー（v2） |
| `NOTIFY_<n>_SECRET` | チャット通知の Webhook トークン/パス または Bot トークン（利用者チャンネルへの投稿権限） |
| `SERVE_AUTH_TOKEN` | 非ループバックの `serve`（リモート/分散アクセス）を守る自動生成 Bearer トークン。値を操作者に表示する唯一の Class A 鍵 |

**保護要件：**
- `--init` / `--update-key` でOSキーチェーンに保管する。`xoksa.env` に記述がある場合はそちらが優先される（例外：`SERVE_AUTH_TOKEN` は**エンジンが自動生成して自身で保管**し、ユーザー登録ではない——§4 参照）
- 管理対象キーはそれぞれ独立したOSキーチェーンエントリ（`Entry("xoksa", "<KEY_NAME>")`）として格納する
- オンデマンド取得のみ — そのキーを必要とするAPIリクエストの直前にのみ取得し、それ以外の箇所では取得しない
- 呼び出しチェーン全体を通じて `Zeroizing<T>` のまま受け渡す。途中で通常の `String` に展開することは禁止。例外：ファイルパーサー（`xoksa.env` ローダー）は行バッファリングと値抽出に標準 `String` を使用する。これらの中間値は最短ライフタイムで関数リターン時に破棄される。ローダー境界を越えて渡される値はすべて `Zeroizing<T>` である。
- `env_map` や `Config` に格納しない
- ログ・デバッグ出力・LLMプロンプトへの書き込み禁止
- `--doctor` / `--check-keys` では存在有無のみ表示。実際の値は表示しない。**例外——`SERVE_AUTH_TOKEN`：** 自動生成（操作者が選んでいない）でリモートのクライアントに渡す必要があるため、要求に応じて操作者に表示する（`xoksa serve --show-token`、および初回生成時に一度）。操作者は OS 信頼境界の内側なので安全。存在確認のための取得はオンデマンド原則の明示的な例外として許容するが、取得した値は `Zeroizing<T>` のまま即時破棄する。APIリクエスト経路外での不要なキー読み出しは避けること。

**HTTP ヘッダー送信境界の例外：**
- `JQUANTS_API_KEY`（`x-api-key` ヘッダー）：HTTPリクエスト境界でキーを `&str`（`&**api_key`）として `.header("x-api-key", …)` に渡す。`reqwest` はこれを `Zeroize` を実装しない内部 `HeaderValue` にコピーするため、最終送信ステップでの許容された例外とする。元の `Zeroizing<String>` はオンデマンド取得され、リクエスト完了時にドロップされる。
- 同じ境界は、HTTP ヘッダーとして送信する他のすべてのクラスAキーにも適用される：分析呼び出しと `/llm net` モデル一覧取得における OpenAI / Gemini / Claude キー、および LINE プッシュの `NOTIFY_<n>_SECRET` Bearer トークン。いずれも借用した `&str` として渡す——OpenAI のキーも LINE のトークンも `reqwest` の `bearer_auth` 経由で、`Bearer …` の値は `reqwest` の内部で組み立てられる——そのうえで `reqwest` が非 `Zeroize` の `HeaderValue` へ唯一の許容コピーを行う。キーを保持する所有 `String` を xoksa 自身のコードで作らず、このヘッダ値を自前で組み立てることもしない。*（2026-10-01 訂正：本項は OpenAI の `Bearer …` 値を `Zeroizing` バッファで構築すると記していたが、実装はそうなっておらず、過去もそうではなかった。`reqwest` に組み立てさせる方が強い——バッファを後から消すのではなく、そもそも作らないため。）*

> **注記：** 認証付きプロキシURL（`user:password@...`）はアプリケーションレベルでは非対応。プロキシ認証はOSレベルで設定すること。

### クラス B — ユーザー識別設定（基本的な配慮）

| 資産 | 説明 |
| :--- | :--- |
| `SEC_USER_AGENT` | SEC EDGARが要求するアプリ名＋メールアドレス（公開識別子であり秘密情報ではない） |
| プロキシホスト・ポート | 接続ルーティング情報（認証情報を含まない） |
| Ollamaホスト・ポート | ローカルOllamaサーバの接続先情報 |
| ユーザー入力文脈 | チャットメッセージ・`-x`引数・`~/.xoksa_history` |
| Debate buffer | 有界コンテキストウィンドウ：LLMレスポンスの抜粋と、それを引き出したユーザーターン（`entry.user`）を含む |

**保護要件：**
- `xoksa.env` にのみ保管。OSキーチェーンは不要
- 不必要にログへ書き込まない
- 認証情報と並べて表示する際は値をマスクする
- Ollama接続先は `--doctor`・`/llm`・`--debug-ollama` での表示を許容する
- **UI 言語は設定であり、画面ごとの好みではない。** `xoksa.env` の `LANG` を唯一の情報源とし、CLI・ダッシュボード（エンジンが配信するページに刻む）・接続画面・設定アプリはすべてこの 1 つの値を読む。ダッシュボードのセレクタは自前のコピーを持たず、この値を書き戻す。OS ロケールは設定が存在しない初回のみのフォールバック。書き込みは**ループバック限定**——LAN のクライアントには設定言語で配信するが、操作者の端末の設定を書き換えさせない——`--private` セッションは書かず、書いたとも報告しない
- チャット履歴（`~/.xoksa_history`）はOSファイルパーミッション（0600）で保護する。`Zeroizing` は不要。`--private` セッションでは読み書きとも行わない——このファイルはユーザー自身が打った文字列の記録であり、無痕跡セッションが排除する痕跡そのものであるため（↑↓キーの呼び戻しはメモリ上で維持）
- ユーザー入力およびDebate bufferの内容は、クラウドLLMモード使用時に選択したLLMプロバイダーへ送信される。これは設計上の動作であり、ユーザーが承知したものとする
- `Zeroizing` は**不要** — 認証情報ではない

### クラス C — 計算済みデータ・公開情報

xoksaが扱うその他すべてのデータはこのクラスに属する。追加のセキュリティ機構を適用するかどうかは、0.1節のCIA評価に基づき個々の資産ごとに判断する：

- テクニカル指標とスコア（RSI・MACD・EMA・フィボナッチ等）— 公開市場データから算出
- ニュース記事のタイトル・URL — 公開情報
- 通常分析のLLMプロンプトとレスポンス — クラスCデータのみで構成（ユーザー入力を含まない）
- 設定値（STANCE・閾値・指標ウエイト・分析モード等）
- ティッカーシンボルと銘柄名
- ログファイル（テクニカル分析結果）

> **注記：** チャットモードのLLMプロンプトは、クラスCデータとクラスBコンテンツ（ユーザーターン・Debate Buffer）を合成して構築される。そのプロンプトのクラスB部分はクラスBの扱いを継承する — 設計上の動作としてLLMプロバイダーへ送信され、ユーザーが承知しているものとする。ログへの書き込みは禁止。

クラス C の資産に `Zeroizing`・セキュアストレージ・オンデマンドアクセスを適用する必要は原則ない。適用するかどうかは、使い勝手とセキュリティ機構のバランスを見て判断する。機密性のないデータに一律適用すると、真に保護が必要な資産がどれかが不明瞭になり、コードの可読性と保守性が損なわれる。

## 0.2 脅威モデル

xoksa は**ローカル・単一ユーザのツール**として動作する。設計は以下の境界を守り、コントロールは §§1–4 に詳述、時点レビューは [security-assessment.md](./security-assessment.md) にある。脆弱性の報告は [SECURITY.md](../../SECURITY.md) を参照。

**信頼境界:** ブラウザ↔ローカルサーバ／ローカルサーバ↔外部プロバイダ（Yahoo・Stooq・Brave・LLM・チャット通知先）／プロセス↔OSキーチェーン。**デスクトップアプリ（Tauri）:** WebView↔デスクトップRust（Tauri IPC・プロセス内）、およびデスクトップと設定アプリ（`xoksa-setup`）↔エンジン（子プロセス。デスクトップは `xoksa serve`、設定アプリは設定系サブコマンド）。§6参照。

**想定する攻撃者（in scope）:**
- **同一ブラウザで開いた悪意あるページ** — ループバック既定の主要脅威：`localhost` へのドライブバイ/CSRF、別セッションのデータへの到達試行。クライアント別セッション分離・`SameSite=Strict` cookie・サーバ側 Origin 検査・`Json<T>` の Content-Type ゲートで対処（§4）。
- **悪意ある上流データ** — ニュースのタイトル/URL・市場データはブラウザに描画される非信頼入力。出力エスケープ＋strict CSP・URL スキーム検査・ニュースを非SOTの「候補」層に留める設計で対処（§§1, 4）。ホストがコード固定でない経路——Ollama（平文 HTTP・接続先は利用者設定）——では、応答本体にも**展開後のバイト数で**上限を置く。`reqwest` は既定で圧縮本体を要求して展開し、宣言された `Content-Length` は圧縮後のバイト数しか表さないため、小さな本体が無制限に膨らみ得る（実測：406 KB → 展開 202 MB → RSS 784 MB）。
- **侵害された/脆弱な依存ライブラリ** — SCA（`cargo audit`＋`cargo deny`＝advisories **及び** ライセンス/ソース遵守、加えて未使用依存を刈る `cargo machete`、毎 push）と、**`#![forbid(unsafe_code)]`**（コンパイラ強制＝xoksa 自コードに `unsafe` なし）のメモリ安全な Rust で対処。リリースビルドは `--locked`。CycloneDX SBOM（`sbom/`）は、出荷しない使い捨ての `cargo auditable` ビルドから生成し、全コンポーネントをインベントリ化して下流解析に供する。
- **ローカルディスク/ログの覗き見** — API キーを OS キーチェーンに保管（平文でディスクに置かず、メモリ上は zeroize）、秘密値をログに出さない、`--private` 無痕跡セッションで対処（§2）。
- **悪意ある/性能の低い LLM 応答** — モデルはプログラム算出値を*説明*できるだけ。整合性ガードが創作値を除去し、将来予測は非SOTとして明示（§1）。
- **改竄されたダウンロード** — アーティファクトごとの SHA-256 公開と、出荷検査をそのハッシュに束縛することで対処（§4・[security-assessment.md](./security-assessment.md)）。

**明示的に対象外（設計上）:**
- **ユーザーの OS アカウントで既に動いているローカル攻撃者** — ユーザー自身の権限で動くコードは OS の信頼境界の内側であり、xoksa は防げない。共有PCの分離は OS の責務（アカウント分離）。
- **非ループバック公開（`--host 0.0.0.0`）** — fail-closed：認証トークン未設定ではサーバが起動せず、接続元はプライベート／ループバックアドレスのみ許可し、安全なリモート利用は**信頼できるプライベートネットワーク内**（LAN、または自分で運用する VPN）で行い、生の公開インターネットには出さない（§4）。多テナント型レート制限は設計上の対象外——単一ユーザの localhost ツール。
- **個人用ループバックツールへのレート濫用/ネットワークDoS** — 接続受入キャップ（§4）以上の多テナント型レート制限は、単一ユーザの localhost サーバには設計上設けない。
- **TLS を実装しない 2 本（エンジン↔GUI、エンジン↔Ollama）** — 外部サービスとの通信はすべて TLS であり、API キーはその経路しか通らない（実測：`src/` に外部プロバイダ宛の平文 `http://` は 1 つも無い）。平文の 2 本は API キーを運ばず、例外は非ループバック時の `SERVE_AUTH_TOKEN` だけである。プライベート空間——ループバック、または自分で運用する信頼できるプライベートネットワーク——を前提とする範囲の決定であり、生の公開インターネットには置かない。
- **認証トークンとセッション cookie を分離しない。** cookie はトークンそのものを運ぶ（§4）。分離にはセッション表・期限・失効が要るが、得られるのは端末ごとの失効だけで、端末 1〜2 台の単一利用者の道具には見合わない。したがって cookie を認証情報そのものとして守る——`HttpOnly`・`SameSite=Strict`・定数時間比較。
- **API のバージョニングと権限分離（RBAC）を行わない。** エンジンと UI は版数一致の対として出荷し、`/api/health` で照合する。役割が 1 つしかない道具に分離すべき権限は無く、パスの `/v1/` は制御ではなく維持対象の在庫になる。トークンを持つクライアントは操作者と同じことが全部できる——これは単一利用者設計そのものであって、その欠落ではない。

## 1. 完全性（Integrity）：データの一貫性と正確性の担保

分析結果の信頼性を維持するため、**単一の信頼可能な情報源（SOT: Source of Truth）**に基づいた設計を採用しています。

#### ● 構造体 `TechnicalDataGuard` によるアクセス制御

指標データの操作は、専用のラッパー構造体 `TechnicalDataGuard` を通じて制御されます。

- **直接アクセスの制限:** 内部データ構造体への直接的な読み書きを制限し、必ずガード（ラッパー）を経由するよう強制しています。これにより、意図しないデータの書き換えや不整合の発生を構造的に防止します。
- **インターフェースの限定:** 各処理に応じた最小限のリード/ライトインターフェースのみを提供し、データの整合性を維持します。

#### ● 確定データのアクセス境界

確定データには、検証を経た経路からしか到達できない。これを担うのは 2 つの境界である。

- **テクニカル（`TechnicalDataGuard`）。** 包んでいるエントリは非公開で、書き込みはすべてセッターを通り、内部への可変参照を返す API も無い。さらに guard は**どの指標が値を生成したか**を記録する。セッターは有限値で呼ばれたときだけキーを記録し、後の再計算に失敗したときは値と記録の両方を消す。したがって生成されなかった値——未計算・計算失敗のいずれも——は**欠損**となり、正常に計算された `0.0` は存在する。判定に必要な区別は「値なし」と「本物のゼロ」であり、この 2 つを分ける。記録の対象は素の `f64` で保持する指標（RSI・MACD とシグナル・EMA/SMA の各脚・バンド上下限・%B）で、これらは `0.0` と「値なし」が区別できないため。既に `Option` で保持している指標（ADX・%K・VWAP・ROC・フィボナッチ・一目・出来高）は型で区別を持つ。ルールとアラートの判定は、このいずれかの形で値が存在するときだけ採用する。期間に対して本数が足りない、または評価に失敗した指標が 0.0 として届くことはないので、`終値 > 長期EMA` のような比較が、生成されなかった値によって成立することはない。欠損指標を参照する条件は false となり、AND／OR の組み合わせ規則は変わらない。バックテストとアラート監視はこの表を同じ関数で作るため、挙動は一致する。
- **ファンダメンタル（`FundamentalData`）。** フィールドは非公開で、**書き込む経路はいずれも書き込む値を検証する**ため、検査を通っていない数値は表示・ログ・LLM への受け渡しに到達できない。プロバイダの取得結果からの初期構築は1つの経路に集約し、そこが取得途中の `FundamentalInputs` を受け取る。`Default` は数値を一切持たない空の値を作るだけ。BPS と価格の後からの更新は検証付きの公開メソッド（`set_bps` / `recompute_derived`）を通り、あわせて比率を更新する。保証しているのは「入口が1つ」ではなく「検査を飛ばせる入口が無い」ことである。非有限値は排除し、正常なゼロと、赤字・負の EPS のような意味のある負値は保持する。PER・PBR・ROE は**確定データの内側で一度だけ**、検証済みの入力から導出する（プロバイダ経路ごとにも、表示経路ごとにも計算しない）。入力または価格が変われば再計算するため、比率だけが古いまま残ることはない。比率の元になった価格も一緒に保持する。信頼できない割り算は比を作らない——フィールドは**値なし**のままで、無限大も NaN も、代わりのゼロも入れない。拒むのは、分母がゼロの場合、`f64` の精度ではゼロと見分けがつかないほど小さい分母（有限だが桁が天文学的な値になる）、および結果が有限でない場合である。百分率は ×100 のあとに再度確認する。有限な比でも、スケールすれば溢れるためである。通貨・単位・対象期間・出典は値とともに保持し、不明な情報は推測で補完しない。

#### ● 独自演算と標準ライブラリの併用による計算精度

計算結果の信頼性を維持するため、以下の設計を採用しています。

- **一回限りの計算実行:** 各指標の計算は実行サイクル中に一度のみ行われます。計算済みデータを共通利用することで、出力形式（画面、ログ、LLM用プロンプト等）によらず、一貫した数値を提供します。
- **標準ライブラリ `ta` クレートの利用:** RSI、MACD、EMAなどの基本的な指標には、コミュニティで広く検証されている `ta` クレートを採用し、再現性を確保しています。
- **独自演算（Proprietary Arithmetic）の検証:** `ta` クレートで提供されていない、または仕様に基づいた調整が必要な指標（ADX、ストキャスティクス、フィボナッチ、VWAP、一目均衡表等）については、透明性を確保した算術式を実装しています。
- **エラー値への対応:** 独自演算において、値幅がゼロ（`high == low`）の場合のゼロ除算回避や、判定境界における丸め処理（eps）を実装しています。これにより、数値計算の破綻を回避し、安全な代替値（中立スコア等）を算出します。
- **数値チェック:** スコア計算および重み付けの過程で、`f64::is_finite()` による有限性チェックと `clamp()` による範囲制約を適用し、極端な数値によるロジックの不安定化を防止しています。
- **精度の統一:** 浮動小数点に関して、すべての内部演算を `f64` に統一し、型変換に伴う精度低下を最小限に抑えています。
- **データ鮮度の管理:** 取引所の更新時刻を考慮した取得ロジックにより、最新の市場データに基づいた分析結果を出力します。
- **将来予測はSOTを改変しない:** チャットモードはオプトインの将来予測機能（`/cast`）を備えます。LLM が計算済みの確定値（価格・スコア・指標値）を書き換えることはないため、完全性は維持されます。予測はそれらの確定値を根拠とした前向きの外挿であり、「予測」として確定データと明確に区別します。予測の根拠となる値は、あくまで本プログラムが計算した値です。

> 各指標の詳細なロジックについては、以下のガイドを参照してください。
> 👉 [xoksa Indicator / Score Guide](../manual/analysis-guide.md)

#### ● LLM出力の整合性ガード（数値はプログラムの仕事であって、モデルの仕事ではない）

SOTの境界は、LLMの**出力**側でも担保します。分析中のあらゆる数値——指標値・スコア・価格——は Rust で計算済みであり、LLMの仕事はその確定値を**推論し言葉にする**ことだけで、創作・単位変換・独自再計算・入力を超えた比較は行いません。プロンプトのフレームでこれを明示し（予防）、出力側の**整合性ガード**でモデルがなお漏らした箇所を捕捉します（検出＋封じ込め）。

- **なぜガードが要るか：** 「捏造するな」と指示してもリスクは下がるが消えません——特に小型／ローカルモデルは、入力に無い数値をなお時折混入させます。予防だけでは完全性ではなく、出力を入力に照らして**検証**する必要があります。
- **何を検出するか** — 数値が、その文の主張する確定データに帰属しない文・行：別銘柄・別指標・別単位・別通貨・別の桁・逆符号・別時点に帰属する数値、確定データに対応が全く無い数値、未提示の価格レンジ（`2600〜2700`）、独自に導いた売買水準、入力外の派生比較（業界平均・利回り等）、算出値と**逆方向**の指標説明（例：確定した VWAP が終値未満なのに終値超と述べる）。
- **何をするか** — **問題のある文・行だけを外科的に除外**し、残りは保持します（警告と除去文字数を表示）。回答全体を pass/fail で採点しません。除外は検証と**同じ文境界**を使うため、通常の散文では、正しい文は誤った文の隣にあっても日英どちらでも残ります——「RSI is 45.2. The price is $999.」は、日本語の同義文と同じく前半を保持します。粒度は行の種類によって変わります：複数の文を含む散文は該当する文だけを失いますが、**表の行・箇条書き・1 文しかない行は行ごと除去**し（半分だけ消えた行は、そうでないデータのように読めてしまうため）、アラートの EXPLAIN 注記は削るのではなく**丸ごと破棄**します（1 行のプッシュに部分的な解説を載せる余地はありません）。**モデル非依存**——モデル名ではなくAPI挙動と入力↔出力の照合に基づくため、モデルが進化しても有効性が保たれます（`--no-ollama-guard` / `OLLAMA_NO_GUARD` で無効化可。`done_reason=length` の打ち切りは無効化時も抑止）。

**照合の基準はどこから来るか——構造体であって、プロンプトではない。** 基準は、確定値を保持するオブジェクト——`TechnicalDataGuard` と `FundamentalData`——から構築し、データとして検査側へ渡す：銘柄・銘柄名・通貨・指標を算出した足・ファンダメンタルが属する会計期間、および確定値ごとの 1 件（指標キー・種別・その値自身の期間つき）。**いかなる文字列も出所として信用しない。** プロンプトは基準になり得ない。プロンプトには会話・利用者自身の発言・他モデルの見解も載っており、そこに書かれたラベルはエンジンが書いたものと区別できないからである（区別できなければ、利用者が打った数字が「確定値」になってしまう）。guard が実際に計算したと記録した指標だけが確定データになるため、計算できなかった指標は 0.0 として確定するのではなく、存在しない。

基準は、それが説明するデータと一緒に動く。**LLM に到達する経路はすべて基準を持つ**——CLI の単発分析、チャットの各ターン、`/basic`、`/forum` とディベート、Web セッション、Web のマルチタイムフレーム分析（足ごとに 1 件、各件が自分の足を名乗る）、アラートの EXPLAIN 注記。再取得では表示テキスト・プロンプト文脈と同時に基準も入れ替えるため、更新後の値は通り、更新前の値は通らない。

**数値は、まず「文中で何をしているか」で読む。** 検証の前に各数値を分類する：**観測値**（述べられた値）、**期間パラメータ**（`RSI(14)`・`MACD(12,26,9)`・`14日EMA`・`1時間足`、フィボナッチ水準を指す `38.2`、`1株あたり` の `1` など）、**日付**（`2026-09-08`・`2019年`・`in 2019`）。値の主張は観測値だけなので、窓長・水準識別子・単位あたりの基準・日付を指標値として照合することはない。年は日付表現の中でだけ年であるから、年のように見える価格（終値 2025）は価格として読む。

パラメータの判定は**構文で行い、位置では行わない**——括弧は検査の免除ではない。期間指定として成立する形（整数、必要なら複数、必要なら足の単位つき）だけをパラメータとするので、`RSI（99.99）` や `RSI (value: 99.99)` は読み取り値の主張として検証する。フィボナッチの比率も、水準であると書かれている場合（`38.2%水準`・`38.2%:`）にだけ識別子として扱い、通常の百分率は観測値のままにする。通貨や単位を伴う数値は、字面が何と読めても金額である——`$5m` は 5 分足ではなく 500 万ドルなので、足を名乗れるのは裸の数値だけとする。

**範囲は文を読む前に確定するので、表記で判定が変わらない。** 数値・日付・期間指定・ティッカーがどこにあるかを**1 文につき 1 回の走査**で決め、その文を読むすべての段——主張の分割と 4 種類の帰属判定、文中のすべての数値——に同じ結果を渡す（各段が独自に導出し直すことはない）。これにより次の対は食い違わず一致する。

- **桁区切り**は数値の一部であって主張の切れ目ではないので、`13,704,000,000,000` と `13704000000000` は同じ挙動になる（同じ文の後半で別の会計年度に転用した場合も同様に拒否する）。`MACD(12,26,9)` の中のカンマも同じ扱いである。
- 同一の**日付**は、`2026-09-08`・`2026年9月8日`・`September 8, 2026` のどの表記でも同じに読む。
- **完全な日付**は観測の時点を示すもので、主張の時点にはしない。時点を与えるのは**年として書かれた**もの（2019年・年度・FY2025・in 2019）だけである。したがって分析を行った日を書いても、対象足と会計年度が異なる通期の数値が拒否されることはなく、同じ文の中の誤った値は従来どおり拒否される。

**免除するのは、本当にそれである場合だけ。** 上記の分類は数値を検査対象から外すため、いずれも接頭辞ではなく**全体の形**で判定する。

- **月名**は実在する名称・略記に限り、前後を単語境界で固定し、日付として成立する構文の中にある場合だけ月とする。開いた読み方は *margin* や *declined* にも一致し、その隣の数値を検査から外してしまう。
- **金額はトークン全体**であり、倍率を含む。接尾辞が数字に直結していても離れていても同じで、`$168.8m`・`$168.8 m`・`$168.8mm`・`$168.8 million` は同一の金額、`$168.8bn`・`$168.8k` は別の金額として読む。百万・十億も英語表記と同じに読む。桁が 3 桁・6 桁ずれた表記は、正しい桁の表記が通るのと同じ基準で拒否する。
- **理解できない接尾辞は読み捨てない。** 検証できない書き方の数値は確定値としない——数字だけ照合して残りを捨てれば `$168.8x` が `$168.8` として通ってしまうためである。序数（`1st`・`3rd`）は位置を数えるものであり、読み取り値ではない。

**判定アルゴリズム——6つの検知器、2つの軸。** いずれもモデルの出力に対し、この基準と照合して実行する。発動しなかった検知器は、その文に触れない。

**検知器は言語ごとに持たない。** 各行の語彙は同じ検知器の日本語表現と英語表現を同居させており、片方の言語にしか無い検知器は存在しない。下表は `--lang en` の回答にも同じように適用される。

| # | 検知器 | 発動条件 | 確定データと照合するか | 捕まえるもの |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 数値の帰属 | 出力に**観測値**として読まれた数値がある | **する**——その文が帰属させている確定値と、銘柄・指標・単位・通貨・桁・符号・時点のすべてで一致すること | 別指標・別銘柄・別足・別単位・別時点への付け替え。算出されていない指標の断定値。単位を伴わない捏造値（「RSI は 99.99」） |
| 2 | 数値単位表現 | 出力に単位つきの数値がある（兆円 / 億円 / 万円 / 円 / % / ％、または trillion / billion / million / yen / usd / dollars / percent / $¥€£） | **する**——ここで報告するのは確定データに対応が全く無い場合。付け替えは検知器 1 が扱う | 数値の捏造 |
| 3 | 裸の価格・レンジ | 出力に 3 桁以上・値が 100 以上の数値がある | **する**——同じ帰属検証 | 確定データが言っていない価格水準 |
| 4 | 独自の売買水準 | 出力に売買文脈語（エントリー / 利確 / 利益確定 / 損切り / 撤退、entry / take profit / stop loss / exit point …）があり、**かつ** 絶対値 100 以上の数値がある | **しない（設計上の意図）** | 数値を売買指示に仕立てること |
| 5 | 入力にない比較・派生指標 | 出力に固定リストの語（業界平均 / 業界の平均 / 業界水準 / 平均的な水準 / 平均水準 / 同業平均 / 同業他社 / 配当利回り / 営業利益率 / 純利益率 / 利益率、および英語11語）がある | **する**——入力に同じ語があれば通過 | **根拠**の捏造 |
| 6 | 逆方向の指標説明 | 出力の VWAP の向きが算出結果と逆（日英とも） | **する**——向きは確定した VWAP と終値から読むため、プロンプトのラベル表記では判定が変わらない | 算出結果を反転させた説明 |

**数値の「検証済み」の意味。** 値だけでなく帰属まで一致して初めて通す。判定は回答単位ではなく、**主張 1 つずつ**に対して行う。1 文が複数の主張を運ぶことは多い——「日足の終値は168.8円、1時間足の終値は170.2円」「revenue was X in FY2025 and Y in FY2024」——ので、修飾（銘柄・足・年）はそれが書かれた主張に結び付ける。主張の切れ目は 、 , ; と *and* / *while* / *whereas* / *but* で取るため、図の**前**に置く日本語の修飾も、**後**に置く英語の修飾も同じように読める。文境界も日英とも読む。英語の `.` は空白か文末が続くときだけ文を終えるので、小数点もティッカーのドットも 2 つの主張を 1 文に混ぜない。

- **どの銘柄か**——同じ主張の中で名指しされた銘柄。したがって「AAPL は $168.8、MSFT は $400」は各数値をそれぞれの発行体に帰属させ、値を入れ替えた対は拒否する。通常語と綴りが同じコード（`IT`）や 1 文字のコード（`A`・`T`）も、読み込み済みならこのセッションの銘柄である——既知銘柄の照合を通常語フィルタより先に行う。
- **どの足か**——同一銘柄を複数の足で読み込んでいる場合、主張が名乗る足の値で照合する。日足の確定値を 1 時間足の値として通すことはなく、分析していない足には確定値が無いので、その足に書かれた数値は拒否する。
- **どの指標か**——同じ主張の中の指標名。ただし**語として**一致した場合に限る。`remains` の中の `ema` や `period` の中の `per` は指標名ではなく、そこに数値を結び付ければ、文が名指ししていないものに帰属させることになる。境界は文字種ではなく英字で見るので、名前の直後に値を続ける日本語（`VWAP168.96`）は従来どおり結び付き、英語の複数形（`prices`・`bands`）も語として数える。具体的な指標語と汎用語を併記しても汎用語を認識するので、「RSI is 45.2 and EMA is 166.88」は各数値を自分の指標に結び付ける。確定値が**まったく存在しない**指標に読み取り値を与える文は、素通りさせず拒否する。
- **どの脚か**——同じ指標の 2 本の脚は計算期間だけが違うので、期間を値と一緒に持ち、期間を名乗る文はその脚で照合する。区別しない言い方（「EMA」）はどちらの脚でも許容し、「長期EMA」で短期の値を引くことは拒否する。日足の分析では `EMA(20)`・`EMA(20 days)`・`EMA（20日）`・`20日EMA`・`The 20-day EMA` が同じ主張であり、月足の分析では `EMA(20 months)`・`The 20-month EMA` が同じ主張である——期間を検証から**外す**読み手と、期間で脚を**選ぶ**読み手が 1 つの定義から語彙を取るため、片方だけが理解する書き方は生じない。計算していない期間（`The 25-day EMA`）には確定値が無く、拒否する。**照合するのは数値であって単位ではない。** エンジンが脚ごとに持つ期間は本数であり、その意味は分析足そのものなので、日足の分析中に書かれた `The 20-month EMA` は 20 期間の脚として通る。文が述べた時間単位と分析足の整合は検証していない。期間はそれが書かれた指標に適用するので、「RSI(14) is 45.2 and EMA is 166.88」の `14` が隣の EMA の脚を選ぶことはない。期間ごとに値を持たない指標（RSI）が、期間を伴うだけで拒否されることもない。
- **単位・通貨・桁**——通貨記号・倍率語・後置の通貨語を一体として解析する。`13704 billion dollars` はドル建ての金額であって円建てではない。倍率は**桁だけ**を表す——万・億・兆や million・billion はそれ自体で金額を意味しないので、株数を「12 million」と書いてよく、「$12 million」とは書けない。通貨は金額にしか付けられないので、`$45.2` を RSI の読み取り値とすることも、`Volume is $1000` と株数を金額で述べることも拒否する。
- **精度**——丸めは、書かれた桁の単位で判定する。確定値 13.704兆円 は「約13.7兆円」と書いてよく、「13.8兆円」は書けない。確定値 168.80 に対する 168.8 は通り、168.9 は通らない。符号は一致必須で、通貨記号のどちら側に書かれていてもよい——`-$2.50` と `$-2.50` は同じ金額であり、確定値 `+2.50` に対してはどちらも拒否する。桁区切りと全角数字は正規化してから比較する。
- **時点**——テクニカルの読み取り値は対象足の年と、ファンダメンタルの値は自身の会計年度と照合する。したがって通期の数値に会計年度を添えても、対象足が別の年であることを理由に拒否しない。年として数えるのは**年として書かれた**もの（2019年・年度・FY2025・in 2019）だけで、完全な日付は分析の実施時刻を示すものであり主張の時点ではない。
- **エンジン自身が述べた条件**——アラートは発火したルール（`score <= 5`）を通知に載せるので、その条件はエンジンがモデルに伝えた内容の一部であり、再掲してよい。文中の比較は語の出現から推測するのではなく**構文として解析**し、解析した指標・向き・等号の有無・値のすべてがルールと一致することを求める。`score >= 5` や `score < 5` は別のルールなので拒否し、ルールが 5.4 のときの `score <= 5` も拒否する——表示丸めが変えてよいのは読み取り値の末尾であって、条件ではない。数値はルールが書いたとおり裸で書かれていなければならない。`score <= $5`・`score <= 5%`・`score <= 5foo` はルールが言っていないことを述べている。比較の**認識**と、条件としての**許容**は別の段階である——閾値に単位が付いた場合、認識されなくなるのではなく許容されなくなるので、読み取り値の照合へ戻さず**条件として**拒否する。戻していたために、終値 3091 の銘柄で `close > ¥3091` が通っていた。日英とも同じに読み、比較は英語では数値の前（`at or below 5`）、日本語では数値の後（`5以下`）に置かれる。演算子が掛かるのは**それが比較している数値**——空白だけを挟んで直後に続く数値——なので、「score is at or below 5（現在のスコアは0.0）」では 5 がルール、0.0 が読み取り値として、それぞれ別に検査される。指標が**その値である**と述べる文（「スコアは5です」）は再掲ではなく、依然として捏造として扱う。さらに、エンジンがルールを述べた指標について条件を書いた文は**条件として**判定しきる。閾値がたまたま現在値と等しい場合でも、向きの違う条件は拒否する（読み取り値としての照合なら通ってしまう）。

会話履歴・利用者の発言・他モデルの見解にしか存在しない数字は確定データに**なり得ない**——そうした行を除外しているからではなく、そもそもテキストを出所として読まないからである。基準は guard とファンダメンタルデータからのみ作る。

**制限（前提を隠さず明記する）。**

- 確定データを**渡さない**経路は 2 つあり、それぞれ「代わりに何を検証するか」を明示する。
  - **銘柄を読み込んでいない自由文の会話**——計算した値が無く、照合先が存在しない。
  - **ニュース仕訳**（`/news` の絞り込み）——渡したタイトルを仕分ける作業であり、数値の出所はタイトルであって市場データではない。ここで銘柄の確定値を渡すと、見出しから正しく引用した数値まで拒否してしまう。

  いずれも従来の存在確認（与えた入力にその数値が存在するか）にフォールバックし、帰属を検証したとは**主張しない**。それ以外の経路では確定データがリクエストと共に運ばれる。Ollama ベンチマークも同様で、分析プロンプトをそのまま流すため、各モデルの行は分析本体と同じ確定値で採点される。
- **ドット無しの大文字トークン**（`MSFT`）を銘柄と読むのは、そのセッション自身の銘柄がその書式である場合に限り、2 文字以上で、かつ guard 自身の語彙にも、列挙した通常語・略語（`I`・`IT`・`AI`・`CEO` 等）にも該当しない場合に限る。したがって日本株のセッション内で引用された米国銘柄コードは「別銘柄」として検出しない（その数値は確定値との照合を受ける）。大文字トークンをすべて銘柄と読む代替案は、正当な文（「I see RSI at 45.2」）を落とすため採らない。
- プロバイダが**通貨を報告しない**場合（ラベル付きの Stooq フォールバック）、書かれた通貨は拒否しない。不明は書かれた内容を否定できず、拒否すればエンジンが持たない知識を主張することになるためである。数値そのものは従来どおり検証する。
- 検知器 5 の語リストは固定の列挙であり、網羅ではない。

1・2・3・4・6 は**数値の捏造**を、5 は**根拠の捏造**——xoksa が検証できない基準——を取り締まる。4 が照合を行わないのは意図的である。確定データに*ある*数値であっても、エントリーや利確の水準として提示された時点でデータが言っていないことになるため、この検知器は数値の**出所**ではなく**用途**を見る。5 がリスト照合であることは、入力が実際にその語を持つ場合に通過することを意味する——ファンダメンタルズに営業利益率が載る銘柄では、モデルはその語を使ってよい。

**意図的に検出しないもの。** 将来に向けた記述は整合性違反ではない。「この勢いなら年内に急騰します」のような文は、数値も価格水準も外部の基準も含まないため、どの検知器も発動せず、そのまま表示される。モデルに見解を求める以上、その見解に推測が含まれることは前提であり、ガードが取り除くのは捏造された数値と検証できない根拠であって、推測そのものではない。将来予測は別扱いで、非SOTとして明示する（前掲「将来予測はSOTを改変しない」）。検知器 5 のリスト外の言い回しによる曖昧な基準（「一般的に」「市場全体では」等）は通過する。

**検知は減点ではない。** 指摘件数はモデルの品質スコアではない。検知の機会は回答が具体的な内容を含むほど増え、何も述べない回答ではゼロになる。したがって件数だけでは評価にならず、出力量とあわせて読む必要がある。


**なぜ重要か——小さいローカルモデルが実用になる。** 数値演算を決定論的なコードが担うため、モデルは持てる能力を「数値の記憶・変換」ではなく**解釈**に集中できます。この役割分担こそが、比較的**小さなローカル（Ollama）モデル**でも実用的な分析を生む理由であり、整合性ガードは弱いモデルの出力を安心して使うための**安全網**です——その数値は決して信頼の拠り所にされないからです。結果として、数値の信頼性を手放すことなく、プライベート・低コスト・オフラインの推論が得られます。

## 2. 機密性（Confidentiality）：機密データの保護

APIキーなどの機密情報およびユーザー環境の保護を徹底しています。

#### ● OS上の一メンバーとしての設計（Rustの活用）

- **メモリ安全性:** Rustの型システムと所有権モデルにより、メモリリークやセグメントエラーを未然に防止します。システムのリソースを安全に利用し、他のプロセスに悪影響を与えない実装を行っています。
- **境界サニタイズの徹底:** ティッカー記号、ニュースクエリ、ファイルパス等の外部入力に対し、許可文字の制限（英数字制限等）や制御文字の排除（セミコロン、パイプ等）を行い、インジェクション等の攻撃リスクを低減しています。動的な識別子（timeframe・指標名）は既知の値（`AnalysisMode` トークン／固定の指標集合）に限定し、入力をそのまま使いません。
- **ファイルパスの解決:** すべてのファイルアクセスにおいて、パスの正規化や存在チェックを実施。想定外のディレクトリへの書き込みや読み込みを構造的に防御します。

#### ● APIキーの管理と廃棄

APIキーは重要な資産であり、その露出時間を最小化する設計を施しています。

- **オンデマンド展開:** APIキーは定常的にメモリに保持せず、リクエスト構築の直前にのみ取得します。
- **ゼロ化消去（Zeroize）:** 利用後のAPIキーが含まれるメモリ領域は、直ちに `zeroize` クレートでゼロ埋め消去します。これにより、予期せぬメモリダンプやトレースによるキー情報の流出を防止します。
- **露出の構造的遮断:** デバッグ出力やログ、内部構造体からAPIキーが露出しないようマスク処理を徹底しています。

#### ● ソフトウェア・サプライチェーンの透明性

#### サプライチェーン・リスクの低減 (`cargo audit` ＋ `cargo deny`)

依存ライブラリに潜む既知の脆弱性リスクを管理するため、RustSec アドバイザリデータベースを用いたスキャンを開発工程に組み込んでいます。

- **継続的な検証**: 全依存ライブラリに対し、毎 push で `cargo audit` を実行し、脆弱性が報告された場合の対応体制を維持しています。同じ契機で `cargo deny` も並走し、脆弱性スキャンでは見えないもの——**ライセンスとソースの適合**——を担います。新しい推移的依存が、許可リストに一度も問われたことのないライセンスで入ってくることがあり、これはテストにも lint にも現れないがリリースを止める事実です。あわせて `cargo machete` が未使用の依存を刈ります。
- **スキャン結果の公開**: リリースごとの SCA 結果を、各現物のハッシュに紐づけて[出荷検査](./security-assessment.md)に記録します。

#### SBOM (Software Bill of Materials) の提供

- **CycloneDX 1.5** SBOM を [`sbom/`](../../sbom/) に、出荷現物のターゲットごとに公開: `xoksa-native-windows-x86_64.cdx.json` と `xoksa-native-macos-arm64.cdx.json`（出荷エンジン・既定 `embedded-ui`）、`xoksa-desktop-windows-x86_64.cdx.json` と `xoksa-setup-windows-x86_64.cdx.json`（§6 の出荷デスクトップシェルと設定アプリ・Tauri/WebView2）、加えて `xoksa-webui-leptos.cdx.json`（WASM フロントエンド・ホスト非依存）。OS ごとに必要なのは、SBOM が*そのバイナリに入っているもの*を列挙するためで、`Cargo.lock` が同一でもプラットフォーム crate は入れ替わる（`schannel`・`windows-native-keyring-store` ↔ `security-framework`・`apple-native-keyring-store`）。使用コンポーネントを機械可読でインベントリ化し、SCA ツールが取り込める。（デスクトップアプリと設定アプリは自前の lockfile を持つ別 workspace で、ルートのビルドでは覛えない。それぞれが自身のインベントリを持ち、エンジンと同じ使い捨て `cargo auditable` 方式で再生成する。）
- **`syft`** で CycloneDX spec 1.5 として生成、リリース毎に再生成（インベントリはバージョン依存）。ネイティブのインベントリは使い捨ての `cargo auditable` ビルドから読み取る——lockfile ではなくバイナリ自身に埋め込まれた依存リストを読むため、*その現物*に入っているものを列挙できる。WASM フロントエンドは自身の `Cargo.lock` から catalogue する（`wasm32-unknown-unknown` のみに解決されるため）。`cargo-cyclonedx` は**使用しない**——`bom-ref` に workspace の絶対パスを書き込み、これを抑止する手段が無く、ツール出力の後編集は原則として認めないためである。正確なコマンドと host ターゲットの注意点は [`sbom/README.md`](../../sbom/README.md) を参照。

#### APIキーの設定方法

APIキーの保管方式としては、`--init` または `--update-key` を通じてOSキーチェーン（macOS Keychain / Linux Secret Service / Windows Credential Manager）に保管する方式を推奨します。各キーは独立したエントリ（`Entry("xoksa", "<KEY_NAME>")`）として格納されます。この方式は、APIキーをプロジェクト設定ファイルに平文で保持することを避けつつ、アプリケーションコード上のオンデマンド取得とゼロ化処理を維持できるため、推奨設定とします。

一方で、従来型のCLI運用を優先する場合、簡易なローカルセットアップを行う場合、またはOS認証ダイアログを避けたい場合のために、`xoksa.env` によるAPIキー設定も引き続きサポートします。`xoksa.env` に同名のキーが記述されている場合は、OSキーチェーンより `xoksa.env` の値が優先されます。`xoksa.env` を利用する場合、ユーザーは適切なファイルパーミッションで当該ファイルを保護する責任を負います。`xoksa.env` から読み込まれた値であっても、ローダー境界を越えて渡される値は `Zeroizing<T>` とし、`env_map` や `Config` に格納してはなりません。

コマンドライン引数によるAPIキーの指定はサポートしません。コマンド履歴やプロセスリストへの露出リスクを排除するための設計上の決定です。

## 3. 可用性（Availability）：堅牢なシステム実行

不測の事態においても分析処理を継続するための設計です。

#### ● 堅牢なエラーハンドリング（Robustness）

- **`unwrap` / `expect` の方針（禁止ではなく「到達可能性」で判断）:** **信頼できない・外部入力に由来する値には使いません**——ネットワーク応答・設定/環境変数・ユーザー入力・untrusted なパース——そうした入力から到達できる panic はクラッシュ＝可用性／DoS リスクになるためで、その経路は `?`・`match`・graceful な継続で処理します。一方、値の存在が証明できる箇所——同一スコープでの確認済み・型/モジュールの不変条件・コンパイル時定数（例：ビルド時に妥当性が確定する静的 `LazyLock` の正規表現 `.expect("valid regex")`）——では `expect("なぜ失敗し得ないか")` で不変条件を明記して用います。起こり得ない場合への過剰なエラー処理は、意図を不明瞭にし、あり得ない失敗を到達可能に見せてしまうため避けます。
- **レジリエンス（回復性）:** APIの応答遅延や設定不備に対し、安全なデフォルト動作を定義することで、ユーザーの分析作業を妨げない可用性を維持します。
- **サーバ／プロバイダ可用性（相互参照）:** ローカルサーバ側は接続受入を上限管理し、遅いチャット1ターンが他エンドポイントを停止させない（§4）。外部データ側はプロバイダ**フェイルオーバー**（Yahoo→ラベル付き Stooq）・タイムアウト・graceful degradation を [security-assessment.md](./security-assessment.md) でカバー。プロバイダの欠損を埋めるために値を創作することはない。

## 4. ローカルサーバ（`xoksa serve`）のセキュリティモデル

ブラウザ・ダッシュボードは、バイナリ**自身に埋め込んだ HTTP サーバ（axum）**が配信します——Apache/nginx も、別のアプリケーションサーバも、言語ランタイムも不要。設計レベルのコントロールを以下に示します。それらを検証する時点レビュー・検証済み SAFE クラス・ペネトレーションテストの playbook は [**security-assessment.md**](./security-assessment.md) にあります。

**既定はループバック。** サーバは `127.0.0.1` にバインドし、ローカルでの利用を前提とします。現実的な攻撃者は、**同一ブラウザで開いた悪意あるページ**（`localhost` へのドライブバイ CSRF）と、**悪意ある上流データ**（ニュースのタイトル/URL・市場データ）です。非ループバックへの bind（`--host 0.0.0.0`）は面を OS 信頼境界の外へ広げるため、**fail-closed**（次項参照）。

**非ループバックへの bind は fail-closed・トークン必須（リモート/分散は信頼できるプライベートネットワーク上で）。** エンジンとUIは設計上分離しており、エンジンを別マシンで動かしリモートから問い合わせる運用を想定する。ただし非ループバック bind（`--host 0.0.0.0`、またはデスクトップの `DESKTOP_LAN_ACCESS` トグル）は**常に認証トークンを有効にして動く**——未設定なら初回の非ループバック起動時にエンジンが **256bit のトークン（OS 乱数・推測不可能）を自動生成**するため、非ループバックのサーバが無認証で動くことはない。トークンは認証情報級の秘密（OS キーチェーン・`Zeroizing`・プロセス引数やログには出さない）。操作者が自分で決める値ではないため、**要求に応じて表示する**——生成時に一度表示し、`xoksa serve --show-token` で再表示——リモートのクライアントを設定できるようにする。これは認証情報の「値を表示しない」原則（§0.1）の明示的な例外で、操作者は OS 信頼境界の内側なので安全。トークンは `--rotate-serve-token` で再生成できる。非ループバック bind されたサーバへの全リクエストはこれを提示する——`Authorization: Bearer <token>` ヘッダ（CLI／API／将来の REST クライアント）、またはブラウザは初回に `/auth` へ POST し、`HttpOnly`／`SameSite=Strict` の cookie（`xoksa_auth`）を受け取る。この cookie が運ぶのは**トークンそのもの**であり、以後のリクエストごとに定数時間で比較する。*（2026-10-01 訂正：本項は「セッション cookie と交換する」と記していたが、それは本サーバが発行しない別のセッション値を指す表現である。両者を同じ値にしているのは意図的な判断で——セッション表が得るのは端末ごとの失効だけであり、端末 1〜2 台の道具には要らない——したがって cookie を認証情報そのものとして守る：`HttpOnly` でスクリプトから隔離し、`SameSite=Strict` でクロスサイト送信を遮断する。）***さらに接続元はプライベート／ループバックアドレスのみ許可する**（リクエスト元に対するプライベート範囲／ループバック検査）。よって非ループバック bind されたサーバはローカルネットワーク内にのみ応答し、**生の公開インターネットには決して置かない**。リモート利用は**信頼できるプライベートネットワーク内**（LAN、または自分で運用する VPN）に留める。

**クライアント別のセッション分離（機密性＋完全性）。** 各ブラウザにランダムな `xoksa_sid` cookie（32桁 hex・`HttpOnly`・`SameSite=Strict`）を発行し、Web セッション状態をその id で名前空間化——`sid|symbol|timeframe` でキー化——することで、**あるクライアントが別のセッションを読む/書き換えることは決してできません**。`HttpOnly` により id はスクリプトから読めず（XSS でも盗めない）、`SameSite=Strict` はクロスサイト cookie 送信を遮断。ループバック既定は平文 `http` のため `Secure` は付けません。

**ブラウザ攻撃面のハードニング（多重防御）。** XSS の一次防御は出力エスケープ——ユーザー/外部由来の文字列はエスケープ済みテキストか HTML エスケープヘルパ経由で描画し、生 `innerHTML` は使わず、ニュース URL はスキーム検査（`javascript:` 遮断）。その上で、全レスポンスに `'unsafe-inline'` を含まない **nonce ベースの strict Content-Security-Policy**（`default-src 'self'`／exfil を塞ぐ `connect-src 'self'`／`object-src`・`base-uri`・`frame-ancestors 'none'`／`form-action 'self'`）、位置情報/カメラ/マイク/決済/USB/モーションセンサを拒否する **Permissions-Policy**、加えて `X-Frame-Options: DENY`・`X-Content-Type-Options: nosniff`・`Referrer-Policy: no-referrer` を付与します。

**リクエストポリシー。** 状態変更 POST は axum の `Json<T>` 抽出器を使い `Content-Type: application/json` を強制します——クロスオリジンの `application/json` POST はサーバが応答しない CORS プリフライトで遮断され、`text/plain` は `415` で拒否。これらの経路にはサーバ側の Origin 検査も併用し、プリフライトが効かない唯一の経路＝`GET`/SSE チャットには明示的な同一オリジン検査を置きます。グローバルな body サイズ上限と保存バックテストルールの件数上限で資源消費を抑え、保存パスは固定（ルール名からのパス注入なし）。

**可用性（自己 DoS 耐性）。** 接続受入セマフォは**同時 256 リクエスト**までを受け入れ、超過分を無制限にキューせず `503` で shed します。数値を明記するのは、上限はそれより小さい対象しか抑えられないからです——以前の `65535` では、ホスト自身の RAM とファイルディスクリプタが先に尽きてしまい、それは `503` ではありません。ブラウザは 1 ホストに 6 接続しか張らないので、単一ユーザのツールにおける 256 はタブ 40 枚ぶんに相当します。許可証はハンドラが応答を返した時点で解放されるため、**稼働中の SSE ストリームは許可証を保持しません**——長いチャットがプールを占有することはありません。したがって許可証が保持されるのはハンドラ 1 つの間であり、その長さは外向きクライアントのタイムアウトで律速され、そのタイムアウト自体にも上限（15 分）を置いて、設定値によって保持時間が無制限に伸びないようにしています。Web セッションは**セッション単位**のロック配下にあり、LLM ストリーミングをまたいで単一のグローバルロックを保持しないため、遅いチャット1ターンが銘柄サマリ等の無関係なエンドポイントを停止させることはありません。

**秘密はブラウザ境界を越えない。** API キーは OS キーチェーンに保管され zeroize されます。JSON API は鍵の**有無**のみを返し、値は返しません。認証情報がブラウザへ送られることはありません。**この HTTP 境界はデスクトップアプリでも不変です:** axum サーバは API キーを一切受け取りません。設定アプリのキーは **Tauri IPC** 境界（ローカル・HTTP を通らない）を通り、子プロセスの stdin 経由でエンジン（`xoksa apply-config`）へ転送されます。キーはローカル WebView の JS 文脈・IPC チャネル・エンジンの stdin のみを通り、Rust 側では `Zeroizing<T>` として扱われます（§6参照）。

> **セキュリティは宣言にとどめず、検証することを目指す。** 各リリースを、利用者がダウンロードする*現物*バイナリそのものに対して検査することを目標とし——上記の Web サーバ・ペネトレーションテストを含む文書化された出荷検査を、そのバイナリのハッシュに紐づけて実測します。静的レビューと動的テストの playbook は [**security-assessment.md**](./security-assessment.md)、リリースごとの結果は[**出荷検査**](./security-assessment.md)に記録します。

#### ● チャット通知（プッシュ）— 送信先はプラットフォーム別の固定ホスト許可リストのみ

`xoksa serve` 内のバックグラウンド監視タスク（プロセス全体で1つ。`serve` の起動中のみ動き、バックグラウンド常駐はせず、ダッシュボードを開いているかどうかにも依存しない）が分足をその足の周期で監視し、利用者が定めた**計算済み値**の条件（例：RSI ≤ 30）が成立したら、チャット基盤へ1行の通知をプッシュする（Slack / Discord / Google Chat は Incoming Webhook、LINE は Messaging API）。評価に使うのは系列の最後の足で、日本株の分足ではリアルタイム気配を含む形成中の足になる。したがって足が閉じるのを待たず、足の途中でクロスを捉えられる。これは判断支援でありアクションではない——メッセージが運ぶのは**計算済み値（SOT）の事実**（銘柄・足の時刻・クロスした指標値・閾値）で、LLM が書く売買文言は載せない（任意の短い解説も、有効時は §1 の出力整合ガードを通す）。監視の対象はセッションではなくルールから来る。各ルールが自分のティッカーを持ち、監視はそのティッカーを自分で取得して再計算する。ブラウザもタブも、特定銘柄を画面に出しておくことも不要で、止まるのは `serve` を終了したときだけである。ルールは起動時に一度だけ `xoksa.env` から読む——ダッシュボードや `/alert` からの変更は即座に反映されファイルにも書き戻すが、ファイルを直接編集した場合は次回起動まで反映されない。

経路は次のように制約する：

- **送信先ホストは固定。** 送信先ホストは**プラットフォーム別の固定許可リスト**——`hooks.slack.com`／`discord.com`＋`discordapp.com`／`chat.googleapis.com`／`api.line.me`——で `https` 限定。利用者が渡すのはホストでない秘密（Webhook トークン/パス、または LINE の Bot トークン＋宛先ID）だけで、許可リストにないホストの URL は拒否する。よって §4 の SSRF 防御——送信先ホストはコード固定で入力から取らない——は維持される。
- **秘密＝認証情報級。** `NOTIFY_<n>_SECRET`（Webhook トークン/パス または Bot トークン）は利用者チャンネルへの投稿権限を持つ。OS キーチェーンに保管し `Zeroizing<T>` で扱い、ログ・プロセス引数・ブラウザ送信のいずれにも出さない。登録は API キーと同じ経路（`--update-key`、またはデスクトップの設定アプリ→子プロセス stdin）で、チャットコマンドでは入力しない。
- **データ POST のみ。** 通知はメッセージを `https` で POST するだけ。シェルを介さず、シグナルで任意コマンド/エンドポイントを実行しない（通知はデータの手渡しであってアクションのトリガではない）。
- **スパム防止。** 同一（銘柄・条件・指標足）につき、条件が偽→真に変わった瞬間だけ1回発火する（ポーリング毎には出さず、条件が真のまま続いても再発火しない）。
- **送信失敗を無言にしない。** 送信は 1 回だけ試す（1 つの不調なチャンネルで監視が止まらないよう失敗は飲み込み、再送もしない）。したがって直近の試行の結果——時刻・成否・理由——をルールごとに保持し、ダッシュボードのアラート欄に表示する。これが無いと、発火して届かなかったルールと、そもそも発火していないルールが区別できない。理由に秘密は含まれない——通知側が URL を含まない形で失敗文を組み直し、秘密を除去する（§0.1）。だから表示できる。
- **`--private` 尊重** — 無痕跡セッションでは通知・URL・秘密のいずれも書かない。

## 5. 配布の完全性とアンチウイルス誤検知

**CLI／サーババイナリ（`xoksa`）** は未署名のネイティブバイナリで、ループバックにHTTPサーバを立て、外向きHTTPS（LLM／市場／ニュース）を行い、APIキーのためにOS資格情報ストア（keyring）を読みます。この**正規の組合せ（ネットワーク＋資格情報アクセス）**こそ、挙動ベースのAV/MLが「怪しい」と採点する典型で、このバイナリが**古典的なマルウェアの痕跡を一切持たない**にもかかわらず、Defender／VirusTotal で**誤検知**が出る現実的リスクがあります。

- プロセス起動・シェル実行なし（分析／CLI／サーバのバイナリで `std::process::Command` を使用していない）。
- `unsafe` なし（`#![forbid(unsafe_code)]` でコンパイラ強制）、Win32/`winapi`/`LoadLibrary`/`VirtualAlloc`/`GetProcAddress` なし。
- レジストリ書込なし、**自己永続化なし（no self-persistence）** — バイナリは autostart 項目もレジストリキーも書きません。パッキング/難読化なし。唯一の埋め込み資産——WASM UI（`include_dir!`）——は正規のアプリケーション資源で、読み取り専用の `.rdata` セクションに置かれ、挙動 ML エンジンがエントロピーを採点する `.rsrc`（アイコン）セクションではありません（2.9.9 の出荷エンジンの `.rdata` は実測約 5.9。ケーススタディが依拠する実測値は v2.6.8 エンジンの約 6.16・多エンジン 0/69である。[av-false-positive-case-study.md](./av-false-positive-case-study.md) 参照）。*適用範囲：これはバイナリの性質です。任意選択の Windows **インストーラ**（§6）は、すべての MSI と同様に `…\CurrentVersion\Uninstall` 配下へ標準のアンインストール項目を登録します——これは OS のアンインストール契約であってアプリの永続化ではありません（autostart は行わず、アンインストールで当該項目も消えます）。*
> **デスクトップアプリ（Tauri・§6）はプロファイルの異なる別バイナリです** — OS の WebView をホストし、`xoksa` エンジンを子プロセスとして起動します。その誤検知対策と署名方針は上記の箇条書きではなく §6 が扱います。

**対策チェックリスト（リリース工程）:**
1. **コード署名（Authenticode、可能ならEV）** — 業界的な決定打で、EV 証明書は SmartScreen 評価も即時に得られる。macOS の成果物は署名＋公証済み。Windows の成果物は現在未署名で出荷し、誤検知はビルド側で対処する（後述・§6）。
2. **配布・検査は release ビルドのみ。** `release` プロファイルを強化済み（`strip = true`・`lto = true`・`codegen-units = 1`）＝小型・シンボルなし。debugビルド（文字列・パス・panic文言・未最適化）は誤検知を踏みやすく、配布・スキャン対象にしてはならない。
3. **再現ビルド＋SHA-256公開** で、成果物がソースと一致することをユーザーが検証可能に。
4. 検知が出たら **Microsoftへ誤検知申請**（＋VirusTotal再スキャン）。署名とダウンロード実績で評価も蓄積する。
5. keyring（資格情報ストア）アクセスは正規機能のため残す。ここでは既知の挙動シグナルとして記録（削除しない）。

**AV 誤検知はビルドで対処する（署名ではなく）。** 出荷 desktop アイコンは非圧縮 BMP フレーム（最大 64×64）に制約し、PE リソースセクションを小さく低エントロピーに保つ——挙動 ML エンジンが採点するのはそこである。手法と再現可能な実験行列は [**av-false-positive-case-study.md**](./av-false-positive-case-study.md)。clean な多エンジンスキャンは監査ではなく、新規ハッシュへの初回スキャンの flag は中身ではなくレピュテーション由来でありうる——各現物のハッシュに束縛したリリースごとのスキャン結果は[出荷検査](./security-assessment.md)に記録する。

## 6. デスクトップアプリ（Tauri）のセキュリティモデル

非CLIユーザーの導入敷居を下げる **Tauri の UI シェルが2つ**あり、どちらもエンジンのコードを一切リンクせず、隣に置かれた `xoksa` エンジンバイナリを**子プロセス**として起動します。**デスクトップアプリ**は接続シェルで、*どのエンジンに接続するか*（`xoksa serve` で自動起動するローカルエンジン、またはアドレス＋アクセストークンで指定するリモート）を尋ね、OS の WebView をそのエンジンのダッシュボードへ向けます。**設定アプリ（`xoksa-setup`）**は独立したアプリで、全設定——API キー・LLM／指標／ニュース／通知・serve のアクセストークン・設定パスワード——をここに集約し、パスワードで保護、デスクトップの **設定** から開きます。分析エンジン・SOT・§4 のサーバ制御はエンジン側のものをそのまま流用し、CLI と `serve --ui` には影響しません。デスクトップは `serve` を駆動し、設定アプリは設定／キーチェーンのサブコマンド（`config-json`／`apply-config`／`settings-password`／`conn-token`／`ollama-models`／`test-notify`／`serve --show-token`・`--rotate-serve-token`）を駆動し、加えて**エンジンの再起動**（`serve --ui`）を行えます——アクセストークンやポートの変更は起動し直したエンジンにしか反映されないため、それらを設定するアプリが再起動もできる必要があります。操作は1つで、何も動いていなければそのまま起動し、自分が起動していないプロセスがそのポートを掴んでいる場合はポート番号を示して拒否します——自分が spawn していないプロセスを kill することはありません。ポート（`SERVE_PORT`・既定 8787）は同じカード上の可視設定であり、env ファイルだけの値ではありません。ここで起動したエンジンは**設定アプリより長生きします**：設定アプリは用が済んだら閉じる一時的なアプリであり、エンジンの寿命をそれに縛ると、設定したばかりの接続が切れてしまうためです。ウィンドウを閉じると子エンジンも終了するデスクトップとは、意図的に異なります。本節はこれらの版に固有のセキュリティ約束＝実装が満たすべき**設計契約**を定めます。

**別バイナリ・別プロファイル。** デスクトップアプリと設定アプリは CLI/サーババイナリ（§5）とは別の成果物です。それぞれ OS の WebView（Windows WebView2／macOS WKWebView／Linux WebKitGTK）をホストし、`xoksa` エンジンを子プロセスとして起動します。この子プロセス起動（CLI は行わない）と設定＋キーチェーンのアクセスが §5 のマーカーを超えて挙動 AV のシグナル面を増やします。誤検知対策と OS 別の署名状況は後述します。

**プロセス起動はシェルを介さない。** どちらのアプリが起動するプロセスもすべて——`xoksa` エンジン（デスクトップは `serve`、設定アプリは `config-json`／`apply-config`／`settings-password`／`conn-token`／`ollama-models`／`test-notify` と、起動・再起動のための `serve --ui`）、デスクトップが設定アプリを起動する経路、OS の「URL を既定ブラウザで開く」ハンドラ——`std::process::Command` に明示的な引数配列を渡す形で、**シェルを一切介しません**。よって引数からコマンドを注入できません。エンジンのパスはアプリ自身の実行ファイル位置（隣に置かれたバイナリ）から解決し、WebView からは取りません。引数は Rust 側で決め、WebView 由来の値は `ollama-models` 用の Ollama ホスト/ポート（クラス B・非秘密）と、開く外部 URL（`http`/`https` スキームに限定）だけで、各々を独立した `argv` 要素として渡し、文字列に埋め込みません。任意のシェル実行を WebView/JS 層に露出しません。

**API キーはローカル経路だけでキーチェーンへ渡る——HTTP サーバは通らない。** 設定アプリは API キー（クラス A）を収集し、**Tauri IPC** 境界経由で設定アプリの Rust コマンドへ渡し、そこから**子プロセスの stdin** に JSON として流してエンジン（`xoksa apply-config`）へ渡します。エンジンが OS keyring へ書き込みます（`keystore::set_key`）。axum HTTP サーバはキーを一切受け取らず（§4 不変）、**キーがプロセス引数になることもありません**。キーはローカル WebView の JS 文脈（リモートオリジンなし・CSP 施錠）・Tauri IPC・エンジンの stdin パイプのみを通り、設定アプリは書込み後に JSON バッファを zeroize し、エンジンはキーを `Zeroizing<T>` として扱います（§2）。`apply-config` は `--init` と同じ headless な apply-setup ロジック（env ファイル＋keychain 書込み）を再利用し、全経路が同一に書きます。設定アプリの**チャンネルテスト**も同じ経路です：`xoksa test-notify` は入力されたチャンネル秘密を子プロセスの stdin で受け取り（argv は通さない）、保存前に疎通を確認できる一方で、秘密がプロセス引数・HTTP 境界・ログに出ることはありません。

**最小権限 capabilities。** 各アプリの Tauri capabilities は必要な分だけに限定します：デスクトップの接続コマンドと設定アプリの設定コマンドを、それぞれのローカル app オリジンに。そしてデスクトップのループバック・ダッシュボードオリジンには窓ポップアップと外部リンクのコマンド＋イベント経路のみ。どちらの WebView にも広範なファイルシステム・任意 `shell`・任意 `http` を与えません。

**単一で安定した設定の場所（SOT）。** `xoksa.env` は**唯一の正準・ユーザースコープのパス**——`<config_dir>/xoksa/xoksa.env`（Windows `%APPDATA%\xoksa`／macOS `~/Library/Application Support/xoksa`／Linux `~/.config/xoksa`）——に解決し、作業ディレクトリに関係なく CLI・`serve`・デスクトップ・設定アプリで共有します。解決は `--env-file <path>` ＞ 正準パス のみ。**暗黙の `./xoksa.env` フォールバックは無く**、起動ディレクトリで設定が分裂しません。起動時に**一度きり・非破壊の移行**で既存設定を正準へインポートします——まず 2.7.1 以前のデスクトップ設定（`<data_dir>/app.xoksa.desktop/xoksa.env`）、無ければ作業ディレクトリの `./xoksa.env` を**コピー**（既存の正準ファイルは上書きしない）——ので更新時も設定が引き継がれます。正準ディレクトリは共有クレート `xoksa-paths` に1定義（engine・desktop・設定アプリが依存＝ドリフト不能）、ファイル解決はエンジンの1箇所（`utils::env_path`）。`--private`（no-trace）の意味は維持します。

**署名。** macOS の desktop・設定アプリ配布物は Developer ID 署名＋公証済み。Windows の配布物は現在未署名で出荷し、各配布物に SHA-256 と出荷検査記録を添付する——署名なしで検証可能にするため。

**ローカル自動起動は自分以外のエンジンを掴まない。** デスクトップがループバックのエンジンを自動起動するときは、固定ポートではなく OS にエフェメラルポートを求める（`:0` に bind → 採番 → 解放）。よって子エンジンは居残りの `xoksa serve` や他プロセスと競合せず、アプリの多重起動もそれぞれ自分のエンジンを持って共存する。WebView を接続する前に、エンジンは `/api/health` で `xoksa-web` として**このアプリと完全一致する版数**を名乗らなければならない（デスクトップとエンジンは対で出荷される）。デスクトップは自分が spawn した子にしか接続しない。LAN アクセス有効時（§4 の fail-closed）は、リモート端末が番号を知る必要のある固定ポートを維持する——spawn 前にそのポートを検査し、占有されていれば占有者を名指しして拒否する。自動起動の失敗はすべて原因つきで報告する（起動失敗・子の即時終了と終了ステータス・ポート占有と占有者・HTTP 401 と到達不能の区別・最終観測状態つきタイムアウト）——素のタイムアウトにしない。エフェメラルポートは永続化しない。

**LAN 公開はオプトインで既定オフ。** デスクトップは既定でエンジンをループバック（`127.0.0.1`）にバインドする。設定アプリの `DESKTOP_LAN_ACCESS` トグルが GUI から `0.0.0.0` にバインドする唯一の経路であり、§4 の通りこの非ループバック bind は **fail-closed——認証トークンが無ければエンジンは起動しない**。接続元はプライベート／ループバックアドレスのみ許可し、安全なリモート利用は**信頼できるプライベートネットワーク内**で行い、生の公開インターネットには出さない。同じ機能は CLI の `xoksa serve --host 0.0.0.0` でも利用できる。

## まとめ

xoksaのセキュリティ設計は、技術的根拠に基づいた一貫性のある実装を目指しています。

計算の唯一性、検証済みの演算ロジック、Rustによるシステム保護、および徹底したメモリ管理は、ユーザーが安全に分析を実行するための基盤として機能します。客観的な事実に基づき、信頼性の高い投資分析環境を提供することが本プロジェクトの設計指針です。
